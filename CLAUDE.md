# CLAUDE.md

Project-specific guidance for Claude Code in this repository. Dense and AI-agent-facing on purpose: an index of pointers, cross-cutting invariants, and non-obvious pitfalls, not a re-explanation of what the code already documents. When a fact already lives in a code comment or docstring, this file keeps only the pointer plus the load-bearing "why".

## Commands

All tooling runs through `uv`.

```bash
uv run discordbot                # run the bot
uv run pytest                    # tests, coverage gate: 80% (--cov-fail-under)
uv run pytest <path> --no-cov    # focused run; without --no-cov a subset exits 1 on that gate
uvx pre-commit run -a            # canonical pre-push check (= make fmt)
uvx pre-commit run ty -a         # type check alone; `uvx ty check` rejects --all-groups (a uv flag)
make gen-docs                    # regenerate docs/ from sources
```

Config comes from `.env` (see `.env.example`): `DISCORD_BOT_TOKEN` + `OPENAI_BASE_URL` / `OPENAI_API_KEY` are the minimum to boot, `GEMINI_API_KEY` unlocks every direct-to-Google path, and the rest are the kill-switches and `MEDIA_HOSTING_*`.

When debugging, check `./data/logs` for the full runtime logs.

Tests share their isolation in `tests/conftest.py` (`economy_isolated_db` / `research_isolated_db` / `fishing_isolated_db` / `memory_isolated_dir`, each swapping the module-level engine or dir onto a `tmp_path`) and their scaffolding in `tests/helpers/` (`discord_mocks.py` fakes an Interaction / Message / followup; `llm_input.py` pulls a named block back out of a recorded Responses request). Reach for those before writing a new fake. Unit tests must inject fake LLM clients and extractors and pass without runtime API credentials; the Tests workflow intentionally provides none.

## Runtime Shape

- `src/discordbot/cli.py` defines `DiscordBot(commands.Bot)`; intents are `Intents.all()` minus `members` and `presences`.
- Cogs load synchronously in `__init__` before the gateway connects. Every cog module exposes a sync `def setup(bot)` and adds the cog with `override=True`; an `async def setup` breaks the first command sync (nextcord schedules it without awaiting). See `_load_cogs_sync`.
- **A cog is a directory holding `cog.py`** (#403). `_load_cogs_sync` scans `cogs/` one level deep and loads `discordbot.cogs.<name>.cog`; everything else in the directory is that cog's own code and needs no prefix. The scan is one level on purpose (a nested helper subpackage such as `gen_reply/link_sources/` carries an `__init__.py` too, and handing one to `load_extensions` aborts boot under `stop_at_error=True`) and raises on a directory that is not a cog rather than skipping it, so a half-finished move cannot silently drop a cog. `cogs/<name>/__init__.py` carries no re-exports (a docstring is fine): a re-exporting one would make `from discordbot.cogs.economy.database import x` execute the whole cog body as a side effect of initialising the package. `tests/test_capabilities.py` walks the same tree with `rglob`, since a non-recursive glob would silently report that no command is runnable.
- **`services/` is the layer below the cogs** (#403): a domain engine two or more cogs need, plus whatever that engine itself needs. `services/economy/` is the ledger every money-moving feature writes through, `services/stock/` the market simulation the economy cog reads a portfolio out of, `services/memory/` the store `gen_reply` writes and the memory cog reads. It is Discord-free and never imports from `cogs/`. Below it, `utils/` and `typings/` carry no domain state and import from neither. A module belongs in `services/` when it is part of the engine itself: a second cog needs it, an engine already there needs it, or it is that engine's own vocabulary — `services/memory/server_prompts.py` has exactly one caller (`gen_reply/cog.py`) and still belongs beside `services/memory/prompts.py` rather than splitting one prompt vocabulary across two layers. Anything else stays inside the one cog directory that uses it.
- The trade this makes is deliberate: a feature that has both a Discord surface and an engine (economy, stock, memory) lives in two paths, split on that seam. Every other cog is one directory.
- Bot presence is hardcoded in `status_task`; there is no DB-backed rotation.
- Add common command errors in `DiscordBot.on_command_error`, not in each cog.

## Cog Rules

- **A user-facing surface is designed in an artifact before it is built.** A panel, a view, a modal, an embed layout or a rendered PNG board is settled by publishing a mockup and reviewing THAT: Discord-faithful chrome, both themes, real copy, and every screen the flow reaches rather than the first one. It catches what prose hides — a status that reads as decoration, a field order that buries the thing the panel exists to track, a control whose scope nobody agreed — and moving a field in HTML costs minutes where moving it in a shipped cog costs a rewrite plus everyone's muscle memory. Put the open design questions on the same page, each with a recommendation, so the answer comes back as a decision instead of a re-derivation. Wording-only work (a command description, one failure line) needs none of this.
- A `nextcord.ui.View` button/select callback must not be named after anything on `View` itself (`refresh`, `stop`, `children`, ...): `View.__init__` runs `setattr(self, func.__name__, item)`, so the name is rebound to the `Button` and the base method is gone. Naming one `refresh` breaks the gateway's `MESSAGE_UPDATE` path (`ViewStore.update_from_message` calls `view.refresh(components)` on every message-tracked view) with `TypeError: 'Button' object is not callable`. No type checker catches it — the decorator retypes the override to a `Callable` alias, which suppresses the override rule — so `tests/test_view_callbacks.py` walks every `View` subclass in the package and fails on any shadowing callback.
- One `commands.Cog` subclass plus a sync `setup` per `cog.py`. **Nothing under `cogs/<a>/` may import from `cogs/<b>/`** — not the cog module, not a helper. Reach across via the bot instance, `typings/`, `utils/`, or `services/`; `tests/test_package_layering.py` fails on a new edge, reading relative and `TYPE_CHECKING` imports too.
- User-facing slash commands need localized name and description for English, `Locale.zh_TW`, and `Locale.ja`.
- A slash option's type comes from its annotation, and nextcord reads `Literal[...]` (turning the members into choices, which an explicit `choices=` then overrides) but rejects an arbitrary `StrEnum` subclass outright, so a shared option vocabulary is a `Literal`: `typings/video.py::VideoQuality` keys `VideoDownloader.quality_formats`, `DouyinDownloader.quality_ratios` and the command's `QUALITY_CHOICES`, each indexed without a default so a wrong preset fails instead of silently downgrading. `SlashOption(default=...)` is deliberately typed `Any` upstream, making the default the one spelling `ty` cannot check; `tests/test_download.py` reads it off the registered command instead. `nextcord.SlashOption` sits in ruff's `flake8-bugbear.extend-immutable-calls` because B008 otherwise fires on any option whose annotation ruff cannot resolve to an immutable type.
- Any user-visible command or behavior change must update `gen_reply/capabilities.md` in the same change and keep `tests/test_capabilities.py` green: its AST scan resolves the whole command tree through the decorated callback (so `@<group>.subcommand` and the nested `/memory server show` both land) and asserts every runnable path appears in that document, matched with a trailing boundary so `/games blackjack_history` never covers `/games blackjack`. A group node is dropped since it cannot be run on its own; a declaration form the scan cannot resolve fails it loudly rather than silently shrinking the set, which is how subcommands went undocumented before #378. The guard is what the deleted `/help` cog left behind and it matters more now, since that document is the ONLY description of any feature anywhere: a command missing from it is a command nobody, the answer model included, can find. The mirror guard (#433) reads the document back the other way: every `/command` it names must be a runnable path or a group node, so a rename cannot satisfy the forward scan under the new name while leaving the old line behind for the answer model to recite in the asker's own language. It takes each mention whole out of its code span, which is what lets a failure quote the stale line verbatim, so a command MUST be written as a code span of its own — a `/name` the reader cannot see, whether loose in prose or buried inside a span that is not itself a command, fails its own assertion rather than slipping past unread (a slash following a word character, `:`, `/`, `.` or `-` is left alone, so a URL, a path and `24/7` are not mistaken for one). Neither direction reaches an inline marker, since it is asked for in plain language and the document describes it that way too, leaving nothing to match on; `markers.py`'s tag set is pinned in the same test instead, so adding or dropping one fails until the document says what the bot can now do or stops claiming what it no longer can.
- For aligned-width embeds use `utils.discord_embeds.embed_spacer_payload(..., target=)` so an edit reuses the uploaded spacer; re-uploading it every edit trips Discord error 400009 on rapidly edited messages (see its docstring).
- Content past embed limits is paginated or rendered to a PNG via `attachment://...`; never truncate silently.
- Never hardcode a Discord attachment-size ceiling: read the destination's real limit through the shared `utils/media_delivery.py::upload_limit_for(guild=...)` (it returns `guild.filesize_limit` so a boosted server's 50/100MB is honored, falling back to 10MB only when there is no guild — DMs expose no per-DM limit). `filesize_limit` is nextcord's boost-tier table lookup keyed on `premium_tier`, not a live field, so it over-reports 25MB for unboosted tier 0/1 (Discord lowered the real base to 10MB in 2024); the guild path keeps trusting it (self-corrects when nextcord refreshes its table). The multipart-envelope margin (`MEDIA_ENVELOPE_MARGIN`, 1 MiB) is held back by `MediaDeliveryPlanner.plan` for a combined edit / an attach riding with embeds (`gen_reply/streaming.py` and `parse_threads/cog.py` pass it; the single-file sites pass 0). Call sites: `parse_threads/cog.py`, `parse_douyin/cog.py` / `video/cog.py` (envelope margin only for a multi-image gallery), `gen_reply/streaming.py`, `gen_reply/cog.py`, `research/delivery.py`.
- **Oversize → URL fallback / unified delivery** (`utils/media_delivery.py`): the attach-vs-host-vs-drop *decision* is unified in `MediaDeliveryPlanner.plan`, which returns a `MediaPlan` (`native` attachments / `hosted_urls` / `dropped_items`). Each feature stays pure: it produces `MediaItem`s (a `source` of in-memory `bytes` OR an on-disk `Path`, plus a `filename` carrying the allowlisted suffix) and hands a list to `plan`; only the actual Discord send + the per-site degradation policy stay local (the sends are structurally disjoint, so unifying them buys nothing). A clip/file larger than `upload_limit_for` is written to an external static host (`MediaHostingService.publish_bytes` / `publish_path`, unguessable name, allowlisted suffix only — mirrors the nginx allowlist, rejects e.g. `.aiff`) and its public URL posted unwrapped (Discord inline-plays it under ~100MB, else a browser link) instead of failing/dropping. Hosted files are **content-addressed** (`<sha256(content)[:32]>.<ext>`): identical bytes dedup to one file (a re-host refreshes its mtime + returns the same URL), written atomically (sibling `.tmp-*` then `os.replace`) so a crash never leaves a poison cache entry. The serve dir **self-cleans** (`MediaHostingService.enforce_cap` size-cap LRU + `cleanup_expired` age-cap + stale-temp sweep, all under a module `threading.Lock`; a recency grace window stops a concurrent publisher reaping another's just-posted URL): each publish enforces `MEDIA_HOSTING_MAX_BYTES` (8 GiB, under R2's 10 GB free tier) eagerly, and the `media_cleanup` cog runs the age (`MEDIA_HOSTING_RETENTION_HOURS`, 168) + size + temp sweep on a `@tasks.loop` + once at startup. The **reaper only ever deletes the bot's own files** — `_HOSTED_NAME_RE` (`^[0-9a-f]{32}\.<ext>$`, ext built from `_ALLOWED_SUFFIXES`, `re.fullmatch`, `is_file(follow_symlinks=False)`, non-recursive) — never a foreign `access.log` / human-named clip in the serve dir. The bot never creates the serve dir (a container-local dir nginx can't see would only 404): a missing dir logs and falls back to host-free delivery, so the docker-compose mount is opt-in, not required for `up`. The size cap + reaper are local-FS-only; a future R2 backend replaces them with a server-side lifecycle rule (content-addressing carries over as the object key). Best-effort: `MediaHostingConfig` (`MEDIA_HOSTING_*`) self-disables when unconfigured (`available`) or when the serve dir is absent, so an oversize item lands in `dropped_items` and **every site degrades to its exact pre-hosting behavior** — `MEDIA_HOSTING_ENABLED=false` (or no serve dir) is byte-for-byte the host-free path. `video/cog.py` dropped its 480p-downgrade retry; the streamer hosts oversized voice/music/inline-image (peeling the largest to a URL when the combined body overflows); `parse_threads/cog.py` hosts only the oversize videos and attaches the rest (per-item, mixed). Wired into IMAGE/VIDEO routes (`gen_reply._deliver_generated_media`, oversize posts a standalone URL message so the persona stream never clobbers it; an unhostable oversize still raises to keep the route's hard-fail path), `video/cog.py`, `parse_threads/cog.py`, the QA streamer, and `research/delivery.py` (an oversize `research.md`/`.png` is linked instead of silently dropped).

## AI Pipeline

### Backend and invariants

- Runtime LLM backend is LiteLLM Proxy behind `OPENAI_BASE_URL`; all runtime conversations use `AsyncOpenAI` and the OpenAI Responses API. Do not switch back to Chat Completions; do not import provider-native SDKs (`google-genai`, `anthropic`) into request paths. The proxy indirection is the point: one OpenAI SDK for the whole project while the backend stays mostly Gemini and any model is hot-swappable via the model string + `extra_body`.
- **Non-proxied paths** are the only runtime calls direct to Google (each builds `genai.Client(api_key=gemini_api_key)` inline as a `cached_property`, no `create_*_client` factory — those are gone, see `research/cog.py` for the pattern; `utils/llm.py` stays as the shared *call* surface, `parse_responses_or_none` / `create_text_or_none` owning the timeout and the degrade-to-None so a one-shot caller only maps None to its own fallback). They forgo proxy-side cost/usage tracking: Gemini Files API attachment upload (`gen_reply/attachment/gemini_file_api.py`) and the linked-post media upload that shares its rationale (`gen_reply/files_api.py`, used by every link builder and by the generated-video persona reply), the YouTube Interactions answer turn (`gen_reply/interactions.py`), omni video generation / editing via the Interactions API (`_handle_video_reply`), the inline `<generate-music>` Lyria render via the Interactions API (`MusicGenerator`, `generation.py`), and deep-research agents (`cogs/research/`).
- On every direct-to-Google path the genai SDK entry point is `interactions.create`; `generate_content` is being deprecated upstream and has zero call sites here, so this is a keep-it-that-way rule rather than a pending migration. Do not reintroduce it, and do not fold its behavior into a measurement of what the native API can do: the two surfaces carry genuinely different capability gates (see Responses API Gotchas for the built-in-plus-function tool case), so a result from one does not transfer to the other. Read the `gemini-interactions-api` skill before writing one: it owns the call shape itself (input parts, streaming, background tasks, function calling, structured output, image / video generation) and it only loads if something makes it, so this line is what tells you to.
- A `google.genai` interaction result cannot be read straight off `interactions.create()`: it returns `Interaction | AsyncStream[...]`, and excluding the stream with `isinstance(x, AsyncIterator)` does NOT clear it, because genai's `AsyncStream` is only structurally an `AsyncIterator` and so stays in the union, leaving every attribute read an `unresolved-attribute`. Declare the attributes actually read as a Protocol and cast to that, as `generation.py::_InteractionResult` does. Naming the type is a separate trap: the module star-imports `Interaction` from both `_gaos.types.triggers` (an alias for the union of the two *request* models, which carry no `output_video` / `status` / `output_text`) and `_gaos.types.interactions` (the response class). `ty` picks the response class, so a nominal `cast("Interaction", ...)` is no longer wrong there, merely insufficient; mypy bound the request union, which is why the docstring warns about it.
- Runtime model strings live in `RuntimeModelCatalog` (`typings/models.py`); each property's docstring carries its callers and tier rationale. **`minimal` is the effort floor, never `none`**: Gemini 3 cannot disable thinking, and LiteLLM only recognises a model as Gemini 3 by the literal `gemini-3` substring — which the `*-latest` aliases dispatched here do not carry — so `none` falls through to the pre-3 branch and sends `thinkingBudget: 0`, which a 3.x model rejects. `tests/test_runtime_models.py` pins it, since the breakage only shows against the live API. The `*-latest` aliases cost a second, unrelated capability: on `interactions.create` both `gemini-flash-latest` and `gemini-pro-latest` are refused native built-in-plus-function tool combination while every concrete model tried accepts it (see Responses API Gotchas), so prefer a pinned model string over an alias wherever a capability gate might key on the name (`fast_model` flash-lite for the route + effort grade, `tool_model` flash for nickname-to-id matching, `slow_model` pinned on BOTH branches with the peak/off-peak split now dispatching two different tiers, `prompt_model` flash+high+grounding for the IMAGE/VIDEO prompt director, decoupled from `slow_model` so its tier tunes alone). `slow_model` is the one tier whose effort is replaced at runtime by the route grade, and the YouTube answer turn hands that effort to `interactions.create` as a `thinking_level`, where the accepted enum is per-model. **An effort's legality is decided by the pair (model string, surface), never by the effort alone**, so a value proven on one says nothing about the other, and that is the check to run before repointing a tier or widening `EffortGrade`. Measured 2026-08-08 against `interactions.create`, three tiers: all three `*-latest` aliases (flash / pro / flash-lite) take only `low` / `high`; `gemini-3.1-pro-preview` adds `medium`; `gemini-3.5-flash` / `gemini-3.6-flash` add `minimal` on top. Anything outside a model's own set is a 400 that loses the whole reply (#459), which is why `slow_model` is pinned and why `minimal` stays unreachable on the pro snapshot only because `EffortGrade` never emits it. On the PROXY every effort is legal on every model, because LiteLLM translates rather than forwards, and which way it translates is that same `gemini-3` substring test: a pinned name sends `thinkingLevel: medium` while an alias sends `thinkingBudget: 2048` (both measured end-to-end; `minimal` on an alias comes back with `reasoning_tokens=0`, so the proxy path genuinely honours it). The trap this sets is that the proxy silently absorbs a pairing the native path rejects, so a tier can look healthy for months and 400 the first time a feature dispatches it direct to Google.
- Author runtime prompts in English (`prompts.py` / `server_prompts.py`, tool descriptions, routing/memory/voice prompts, `TTS_STYLE_DIRECTIVE`); reply *content* is localized at runtime by the in-prompt "follow the user's language" rule, not by writing the prompt in another language. Deliberate exceptions: the few load-bearing Chinese behavior notes in `COMMON_PROMPT` (e.g. the 轉帳 caution); the bot's own name 破貓.
- **Generated media style defaults**: IMAGE and VIDEO deliberately carry NO default aesthetic; visual style is left entirely to the model (the `IMAGE_PROMPT` / `VIDEO_PROMPT` refine directors, the `INLINE_IMAGE_INSTRUCTION` / `VIDEO_INSTRUCTION` markers, and the `ImageGenerator.render` empty-prompt fallback all stay style-neutral). Only MUSIC (`MUSIC_INSTRUCTION` + `MUSIC_STYLE_DIRECTIVE`, Japanese anime / J-pop with Japanese lyrics) and VOICE (`TTS_VOICE` / `TTS_STYLE_DIRECTIVE`, a fixed 18-year-old woman's timbre) keep a deployment default; VIDEO additionally keeps the spoken-language order (Chinese > Japanese > English-only-on-explicit-request) in `VIDEO_PROMPT` / `VIDEO_INSTRUCTION`. Do not reintroduce a code-side static style suffix for image/video: it can't honor "unless the user specified".
- LLM SDK objects are named `responses`; loop items are named `response`.
- LiteLLM's docs lag its code — answer proxy-behavior questions (request translation, `extra_body`, tool/grounding quirks) from its source, not its docs. `~/repo/litellm/` carries no library source: it is the proxy's deployment config, useful for which models and settings are live and which image the proxy pins. The source itself arrives transitively via `openai-agents[litellm]`, so read it in the uv env (`uv run python -c "import litellm, os; print(os.path.dirname(litellm.__file__))"`, version in `uv.lock`); when the answer depends on a version this env does not have, shallow-clone upstream into a scratch dir and read that instead. The uv copy is for reading; the authority on runtime behavior is the running container, which can drift from it, so confirm with `docker exec litellm-litellm-1 python -c "import importlib.metadata as m; print(m.version('litellm'))"` and read its source under `/app/.venv/lib/python3.13/site-packages/litellm`.
- For Discord embeds prefer `media.discordapp.net` `proxy_url` over origin URLs (CDN links expire).

### Reply pipeline (`gen_reply` orchestration)

- **Dual render from one history walk**: `_fetch_history` does the single channel-history read. `_get_reference_and_current(text_only=True)` feeds routing and, only when an optional alias candidate exists, the narrowed memory selector; that selector also renders `_render_history(text_only=True)` on demand (`[attachment: kind]` markers, no upload). The uploaded-`file_id` render (`_render_history(text_only=False)` + `_get_reference_and_current()`) is awaited only by the answer, so the route never blocks on the Files API and a selector that actually runs still overlaps the upload window.
- **Route is two parallel calls under one `route_done` gate**: `_route_classify` returns `RouteClassification` (only critical-path call, gates dispatch); `_grade_effort` returns `EffortGrade` concurrently. QA/SUMMARY override the slow model's effort with the grade (footer shows `model (effort)`); IMAGE/VIDEO cancel the effort task. Optional memory selection + effort grading share the `route_done`-gated `_await_gated` helper (unbounded while the route runs, then only a grace: `MEMORY_SELECT_GRACE_SECONDS` / `EFFORT_GRACE_SECONDS`). On timeout/error effort falls back to `high`; memory selection keeps the code-resolved author / reply-chain / explicit-mention memories and omits only the optional third party.
- **Speculative `ReplyContext`** (`_prepare_reply_context`): history + server memory + deterministic participant memory + optional alias selection built concurrently with the route. IMAGE/VIDEO consume it (not cancel) — awaited only after the media is on screen so its build overlaps generation; the reply injects `memory_block` but never `server_memory_block`. SUMMARY rebuilds at `history_limit=200`, `memory_enabled=False`, reusing shared parts.
- **Streaming UX** (`streaming.py`): progress is reactions on the user's message (`ReactionStatusChain`, ordered, fire-and-forget, custom app emojis); no separate status messages. `ResponseStreamer` previews the reasoning summary as `-#` subtext, replaced by the first content delta. Edits run on a snapshot editor task that shuts down via a stop-event (not cancellation) so an in-flight write always lands before the final edit (else it orphans the reply). `_reply_or_send` degrades `message.reply` to `channel.send` on a deleted source (Discord 50035 / `NotFound`).
- **Best-effort convention** (voice, inline image, image/video persona replies): any failure leaves the primary deliverable plus a ⏱️/⚠️ react hint on the source, never raising into the pipeline's outer error path. An oversize clip/image is hosted as a URL first (the decision lives in `utils/media_delivery.py`; see the oversize → URL fallback in Cog Rules); only an unhostable one falls back to the drop + ⚠️ hint.
- **Kill-switches** (`LLMConfig`, runtime; off still strips any marker but produces nothing): `youtube_video_enabled`, `deep_research_enabled`, `inline_voice_enabled`, `inline_image_enabled`, `inline_music_enabled`, `inline_video_enabled` (the last two gated through `music_available` / `video_available`, which also require `gemini_api_key`, like `deep_research_available`), `douyin_video_enabled` / `bilibili_video_enabled` (each guarded inline with a `gemini_api_key` check via its `_*_media_ingest_allowed` predicate, like `youtube_video_enabled`; off still injects the linked post's text, it just does not fetch the media). `DouyinConfig.auto_expand_enabled` lives in `typings/douyin.py` instead, since auto-expansion is not an LLM feature. `image_refine_prompt_enabled` / `video_refine_prompt_enabled` are the odd ones out (split per route: each gates its own `PromptGenerator.refine` step, not a marker; off sends the raw request straight to the model).
- **Logfire spans**: `gen_reply pipeline` / `route` / `effort` / `context build` / `memory selection` / `answer` (carries a `backend` attr) / `image reply` / `video reply` / `threads context` / `douyin context` / `bilibili context`, plus first-reasoning-delta + first-content-delta logs in `streaming.py`.

### Routes

- **QA** (default): answer streams with the built-in `googleSearch` / `urlContext` tools; carries the inline voice/image/music/video markers and the deep-research marker. It is also the only route carrying the **capability reference** (`gen_reply/capabilities.md`, rendered by `capabilities.py`, gated by `_handle_message_reply(describe_capabilities=...)`): the English feature document that replaced the deleted `/help` cog, read once at import and injected as a `role=assistant` block at the FRONT of the answer input, ahead of history — it is the one block that is byte-identical on every reply, so the front is where it costs least against a prefix cache. One English document instead of the three hand-maintained locales the cog carried, since the answer model translates it into whatever language the asker used; its framing line says it is authoritative about what exists but must never be recited unprompted, or a catalogue on every turn reads as an invitation to advertise. SUMMARY leaves it off (a channel digest is not a question about the bot), and the media persona replies never see it.
- **SUMMARY**: rebuilds at `history_limit=200`, no memory, no selection. A URL-bearing SUMMARY is rerouted to QA by `_route_classify`.
- **IMAGE** (`_handle_image_reply`): the raw request is first expanded by `PromptGenerator.refine` (`prompt_model` flash+high + grounding, `IMAGE_PROMPT`, kill-switch `image_refine_prompt_enabled`, best-effort so a director failure falls back to the raw prompt) then renders via `ImageGenerator.render` (an empty edit prompt falls back to a Chinese default; one retry on an empty result before raising). Edit needs raw pixels, so it loads bytes via `get_image_source_bytes` (not Files-API handles) and passes them as input images — to both the refine (as grounding) and the render. Image sent first; then a best-effort persona reply (`IMAGE_REPLY_PROMPT`, `media_reply_model` flash+low, no tools) via the shared `_stream_media_persona_reply` (history + selected user memory, never server memory), so a reply failure never disturbs the delivered image.
- **VIDEO** (`_handle_video_reply`): native Gemini omni via `VideoGenerator.render` (`interactions.create` DIRECT to Google, the Interactions API is Gemini-only; the single downstream video render in `generation.py`; the route takes the raising `render` since video is always the primary deliverable). 16:9 for pure text only (an image request omits the aspect ratio since omni may infer image_to_video, which follows the source frame's ratio; an edit omits it — omni 400s it — and keeps the source clip's ratio), `delivery="uri"` (the clip returns as a Files URI, no base64 bloat, downloaded via `_download_output_video` — a bounded download-retry, NOT an ACTIVE poll: `files.get` can report `PROCESSING` right after the interaction is `completed` even though `files.download` already serves the finalized bytes, so retrying the download directly is both correct and lower-latency than waiting for ACTIVE); duration is omni's default. Three input modes by precedence: a source video on the message / replied-to message is uploaded to the Files API and edited in place (`get_video_sources` raw bytes, `task="edit"`, the raw request as the literal edit instruction, and the prompt director is SKIPPED — it only grounds on image parts, so a video-only edit would run it blind and add latency; omni takes a single input here so accompanying reference images are dropped); else the request is expanded by `PromptGenerator.refine` (`VIDEO_PROMPT`, flash+high+grounding) and up to `MAX_VIDEO_REFERENCE_IMAGES` message + replied-to images ride inline as `(bytes, mime)` reference pairs (each image MUST carry its real mime — an empty mime 400s omni "Unsupported MIME type: ", the bug that broke image-to-video); else plain text. ### Inline markers (`markers.py`, `generation.py`)

- The answer model self-selects, inside its own output, which spans to speak (`<generate-voice>...</generate-voice>`, kept visible) and which images / music / video to attach (`<generate-image>...</generate-image>`, `<generate-music>...</generate-music>`, `<generate-video>...</generate-video>`, removed from visible text so the prompt never leaks). Markers may repeat where it makes sense: every `<generate-voice>` span is concatenated into one clip and every `<generate-image>` block becomes its own attachment, while `<generate-music>` and `<generate-video>` are single-per-reply (first non-empty kept). The decision stays inside the answer model so text, clip, and media stay coherent (a post-hoc classifier wouldn't). The tags are deliberately hyphenated (`generate-*`, like `<deep-research>`) so none collides with a real single-word HTML / SVG / SSML element (`<video>` is HTML5, `<image>` is SVG, `<voice>` is SSML); a bare `<video>` would otherwise let a reply that merely SHOWS example markup be pulled as a generation request and stripped, even in a disabled deployment (extraction runs regardless of the kill-switch). `extract_inline_markers` pulls them all at finalize; `scrub_markers_for_preview` hides tags from the preview (image/music/video hidden as they stream, voice kept). All run after the text is on screen (zero added latency) and ride a single `Message.edit(files=[...])` carrying the voice clip plus every other attachment — `edit` replaces the attachment list, so two edits would drop the earlier files. None adds a function tool on the answer turn, so none has to carry the tool-mixing flag.
- **Voice** rides QA+SUMMARY (`allow_voice`, `COMMON_PROMPT`): the wrapped segments are concatenated in order into one `VoiceGenerator` input, no spoken-length cap by design (the prompt tells the model multiple spans stitch into one clip, so it tags only the worthwhile lines instead of the whole reply). TTS quirks in `generation.py`'s `VoiceGenerator` docstring: the proxy ignores `instructions`, 500s on `response_format` (style rides in the input prefix, output WAV), single fixed `TTS_VOICE`. **Image** is QA-only (`allow_image`, `REPLY_PROMPT` + `INLINE_IMAGE_INSTRUCTION`): each `<generate-image>` description is rendered best-effort by `ImageGenerator.generate` (twin of the IMAGE route's `render`, one implementation); up to `MAX_INLINE_IMAGES` (9, so the voice clip + images fit Discord's 10-attachment cap) render concurrently in `_build_image_candidates` and ride the one edit, extras hard-dropped. When the user uploaded image(s), `_build_image_candidates` loads them (`_load_marker_source_images` returns `(bytes, mime)` pairs, via the streamer's `input_builder`, mirrors the IMAGE route's current + replied-to gather; the edit path strips the mime) and passes the bytes so the `<generate-image>` **edits** them instead of generating fresh. Unlike the IMAGE route, the marker description is NOT run through `PromptGenerator` (the answer model already authored it with grounding), so `image_refine_prompt_enabled` does not affect it. Deliberately separate from the IMAGE route (image-first UX); routing decides which runs first so they never double-fire. IMAGE/VIDEO routes never speak or inline-image. **Music** is QA-only too (`allow_music`, `REPLY_PROMPT` + `MUSIC_INSTRUCTION`, gated on `music_available`): one `<generate-music>` block per reply (first non-empty, single clip by design) renders best-effort via `MusicGenerator.generate` (direct-to-Google Lyria on the Interactions API, non-streaming) in `_build_music_candidate`; the style defaults to Japanese anime / J-pop *with Japanese lyrics* (Lyria picks the lyric language from the prompt, so the language is defaulted, not just the genre; steered in the prompt, reinforced by `MUSIC_STYLE_DIRECTIVE`) but the model departs for a genre/language the user asks for or an instrumental. The clip rides the same single edit; its extension follows the returned audio mime (`music_filename`). Unlike the voice clip, the bot's own music attachment is NOT skipped from later history input (`input.py` skips only `reply.wav`): the `<generate-music>` description is stripped from the visible reply, so the clip is the only trace of the song and is deliberately re-ingested so a later turn can reference it. **Video** is QA-only too (`allow_video`, `REPLY_PROMPT` + `VIDEO_INSTRUCTION`, gated on `video_available`): one `<generate-video>` block per reply (first non-empty, single clip by design) renders best-effort via `VideoGenerator.generate` (the best-effort twin of the VIDEO route's raising `render`, one implementation, direct-to-Google omni on the Interactions API) in `_build_video_candidate`. When the user attached image(s) they ride as `(bytes, mime)` reference pairs and omni infers the task (reusing `_load_marker_source_images`); otherwise plain text-to-video (source-video in-place editing stays the VIDEO route's job). `VIDEO_INSTRUCTION` caps it at ONE clip per reply as a plain capability limit, NOT a cost warning (telling the model a clip is expensive makes it over-refuse). Almost every clip exceeds Discord's upload limit, so `MediaDeliveryPlanner` hosts it as a URL; the shared `source_images_task` loads uploaded `(bytes, mime)` pairs once even when `<generate-image>` and `<generate-video>` both fire, since `load_image_bytes` re-fetches per call.

### Attachments (`gen_reply/input.py`)

- Ingestion is gated by `get_supported_modalities` for the slow model (`MessageInputBuilder._supported_sources`); unsupported attachments are dropped before any LLM call. Images downscale to 3072px longest edge (`utils.images.shrink_image_bytes`) first.
- **Forwarded messages**: a Discord forward leaves `content`/`embeds`/`attachments` empty and puts the original payload in `message.snapshots` (`List[MessageSnapshot]`, stickers as `sticker_items`). `get_cleaned_content` folds each snapshot's text in tagged `[forwarded message]` (appended, so a forwarder's own comment is kept), and `collect_attachment_sources` collects each snapshot's media via the shared `_sources_from_parts`, so a forward is never blank. Detection is just non-empty `message.snapshots` (no `reference.type` check); a normal message has none, so behavior is unchanged.
- **Provider-aware** via `build_attachment_handler` (`attachment/select.py`, `"gemini" in model_name` over `slow_model.name`, returning `GeminiFileUploader` vs `InlineRenderer`; the `OpenAIFileUploader` / `AnthropicFileUploader` / `GrokFileUploader` branches and their modules are scaffolded-and-commented until their reference path is verified, like `games/lobby.py` — do not delete them as dead code; the Grok one uploads only files, direct to `api.x.ai` since LiteLLM refuses `create_file` for xai, and keeps images inline because xAI resolves no image file id): a non-Gemini answer model can't resolve a Gemini Files URI (the proxy mistranslates it), so its attachments are inlined per type by `InlineRenderer` (image base64 via `render_image`; PDF base64 / UTF-8 text / else dropped via `_inline_file_part`; needs no `GEMINI_API_KEY`). Gemini is the default (also ingests video, hits the inline cap sooner): it uploads every supported attachment to the Files API and references the full `uri` as an `input_file` `file_id`, never base64 (avoids the per-part `inline_data` cap; the bare `files/<id>` name fails the proxy's mime lookup).
- Upload/adopt mechanics are in `attachment/gemini_file_api.py` + `attachment/base.py` docstrings (the per-message LRU cache stays in `input.py`): `_upload_file`'s 15s ACTIVE-poll + the deprecated-`uploaded`-status / "not in an ACTIVE state" 400, `PendingUpload` / `_resolve_file_upload` re-poll-and-adopt with a lazy `load_data` (no re-download), and the per-message LRU cache (keyed on message id, edit time, `collect_attachment_sources` ids). Media fetch + upload is bounded by `MEDIA_CONCURRENCY` (`_media_semaphore`, shared on the singleton builder so concurrent pipelines don't starve each other); URL fetches use a 10s timeout; a failed-fetch source is skipped for `DEAD_SOURCE_TTL` so an expired-CDN attachment in scrollback isn't re-fetched and re-warned every reply.

### Responses API Gotchas

- Strict role/content part pairing: `user` / `system` / `developer` use `input_*` parts; `assistant` uses `output_text` or `refusal`. So a message with attachments falls back to `role=user` (see `_assemble_input_message`). Prefer string-content shorthand when there are no attachments.
- The top-level `instructions` parameter has `developer` authority and outranks everything in `input`, but does not persist across turns. Put behavior rules there (or in `COMMON_PROMPT`), never in an input-side wrapper.
- Separator messages use `role=system`, not `developer`, for Gemini and Claude compatibility through LiteLLM.
- Grounding is reported differently per surface, so a check that knows only one shape reads a grounded reply as ungrounded: the Responses bridge emits ONLY `annotations` of `type: url_citation` (urls are `vertexaisearch.../grounding-api-redirect/`) and carries no `groundingMetadata` anywhere, while chat completions and the native API do carry `groundingMetadata` / `webSearchQueries`. Run a builtin-tools-only positive control before reading any zero as an absence; three separate investigations called a grounded reply ungrounded for want of one.
- Mixing a custom function tool with the built-in `googleSearch` / `urlContext` in one Gemini request DOES work; what it takes differs per surface, and both surfaces were measured live in 2026-07 (proxy path against the running LiteLLM 1.93.0, native path both direct to Google and through the `/gemini` pass-through, which proved byte-transparent). Through the LiteLLM proxy it needs `include_server_side_tool_invocations: true` flat in `extra_body`. Without that flag LiteLLM strips the search tools client-side before dispatch (`_resolve_search_tool_conflict`) and the reply degrades to zero annotations with no 400; the silence is LiteLLM's, not Google's, whose own answer to the unflagged mix is a hard 400 naming the flag. With it LiteLLM emits `toolConfig.includeServerSideToolInvocations` (`vertex_ai/gemini/transformation.py:1167`) and grounding survives at full strength, equally on Responses, Responses-streaming and chat completions, and on `gemini-3.1-pro-preview` as on flash. On `interactions.create` that flag is unsettable (`Unknown parameter 'tool_config'`) and unnecessary: every concrete model tried combined natively (`gemini-3.1-pro-preview`, `gemini-3.1-flash-lite`, `gemini-3.5-flash`, `gemini-3.6-flash`) while BOTH `*-latest` aliases were rejected. Only the behavior was measured, not the cause, but it rhymes with the alias-does-not-carry-the-substring trap `RuntimeModelCatalog` documents for effort, so treat a bare alias as suspect wherever a capability gate might read the model string. Do not re-derive any of this from LiteLLM's source alone, and do not trust a single sample: the drop warning (`vertex_and_google_ai_studio_gemini.py:569`) is deduplicated, so its presence in the proxy log is not a per-request signal, and the proxy runs `cache: true` with a key that ignores `extra_body`, so a flagged request silently replays an unflagged cached answer unless the prompt carries a nonce AND `extra_body` carries `{"cache": {"no-cache": true}}`. Both traps produced confidently wrong readings before they were caught. What has NOT been lifted, re-measured 2026-07 at N=20 per condition on `slow_model`: one turn never carries both, rather than carrying both unreliably. A function call ends the turn with empty text (145/145), so no grounded *answer* can ride a lookup; whether a server-side search silently ran on that turn is unmeasurable, since there is no message item to hang annotations off. The second turn with the tool result fed back does ground (19/20), and streaming behaves identically to non-streaming. Three traps before adding any function tool to a turn that also searches, all measured: the answer turn's `extra_body` does not set the flag today and is safe only because no function tool rides it, so attaching one without it silently ends grounding on every QA reply; merely *offering* the tool made the model call it on a pure-search question 20/20 and zero the grounding, and the restraint wording already in `MEMORY_SELECT_PROMPT` does NOT fix that (10/14 still spurious) while a sentence explicitly exempting live-external-fact questions does (0/14); and naming a tool in `instructions` without attaching it makes the model hallucinate that call (3/12), which ends the turn just as a real one would.
- The code-execution built-in tool is intentionally omitted from `ModelSettings.tools`: providers validate every uploaded file part against a narrow MIME allowlist and 400 the whole request on video / audio / GIF-as-video, so it can't coexist with the Files-API attachment path. The search/url tools have no such limit.
- Gemini prepends leading newlines to the first reasoning and content delta; `_on_reasoning_delta` / `_on_content_delta` strip them. Gemini thought summaries only flow through the Responses API.
- `client.images.edit(image=...)` needs raw `bytes`, not image-reference dicts.
- **Media reaches the model by upload, never by URL.** Upload it to the Gemini Files API (`gen_reply/files_api.py`) and reference the full `https://.../files/<id>` uri as an `input_file` `file_id`. Handing over a remote http(s) `file_id` / `file_url` looks equivalent and is not: LiteLLM rewrites it with `convert_url_to_base64` into `inline_data` (`llms/gemini/chat/transformation.py:151`), so the media starts counting against the request body and a failed fetch is swallowed by a bare `except Exception: pass`; a Files uri instead hits a dedicated no-fetch pass-through (`llms/vertex_ai/gemini/transformation.py:560`). The native Interactions path is stricter still — no proxy in the loop, and it resolves only Files uris and YouTube links, so a URL there reaches Gemini unusable. Bytes already in hand may be inlined as a `data:` URI (that fetches nothing). the Threads link builder (now `gen_reply/link_sources/threads.py`) was the last exception and was migrated in #341; `tests/test_model_media_parts.py` keeps it that way.
- Per-token pricing comes from `utils.model_pricing` and its cached LiteLLM JSON; do not hardcode rates.

## Fishing

- `/games fishing` is a single-player, LLM-free mini-game under `cogs/games/fishing/`; state lives in `games.db` through the fishing-owned engine, wallet cash stays in economy. One public message edited in place, opener-only, self-deletes after 180s idle. Stock and fishing share `utils/owned_message_views.py`: subclass `OwnedPublicView` and edit through `edit_owned_public_message(...)`.
- `fish_grade_config`, `fish_species`, and `fishing_gear` are the tunable source of truth, seeded offline; `defaults.py::build_default_catalog` is the one catalog definition and `scripts/seed_fishing.py` is the only thing that carries it into a deployed `games.db` (idempotent, `--dry-run` prints the pending diff field by field). Retuning `defaults.py` without running it changes nothing in production.
- `catch.py` is pure and RNG-injected. Luck is the additive rod+bait `rarity_shift_bps`, read as ONE rarity step and **compounded** over the grade's rank; `compose_grade_weights` never moves the most common grade and the clamp (`LUCK_STEP_*_BPS`) bounds the step, not the finished factor. Compounding is load-bearing, not a flourish: base weights decay geometrically, so the pre-#351 factor that grew linearly converged on weights proportional to `weight * rank`, capping 神話 at 1.53% of rolls however large the shift got and landing most of the moved mass on the second-commonest grade; with the clamp it shipped with, the whole ladder's EV topped out at 2.45x its floor and then FELL BACK to 1.87x. The exponent is a grade's POSITION in `order_index` order (ties sharing one), never the raw value: `order_index` doubles as the display order, so a 0/10/20/30/40 catalog is an ordinary thing to write and a raw exponent turns it into 94% 神話, while a tie would otherwise be broken by whatever row order SQLite returned.
- **Fishing is deliberately NOT a sink** (#351, replacing the net-deflationary rule): every combo returns at least its per-cast cost and at most 1.7x it, upgrading either the rod or the bait raises both the return and the rare-catch rate, each grade's payout band sits entirely above the grade below it ON THE SAME BAIT (the bonus scales grades alike, so a 稀有 on 路亞 does outpay a 史詩 on 蟲餌), and a 傳說 never surfaces under 2.00x (size bands are per grade, so `CatchRoll.size_rank_bps` — position inside the species' own band — is what the 大物 marker reads, not the raw multiplier). `tests/test_fishing_catch.py` computes all of that EXACTLY rather than by sampling, since adjacent rungs differ by ~1 point of return; one seeded simulation pins that arithmetic against `roll_catch`. The top combo lands well above break-even by construction, not by slack: per-cast cost is additive (amortized rod + bait) while the value gear buys is multiplicative, and monotonicity has to hold on EVERY pairing, so the top rod paired with the cheapest bait caps its amortization and the cheapest rod paired with the top bait caps that bait's price. Those two caps put the top combo above ~1.3x for any pricing at all. The 1.7x is a ratio and bounds no absolute rate: minting runs +2.9 per cast on starter gear to +88 on top gear, and there is no cast cooldown. Catches still cap at `FISHING_MAX_SINGLE_CATCH`. Purchases burn via `apply_ordered_wallet_deltas`; payouts credit via `credit_with_repayment`, which does NOT divert to loans (passive income stopped auto-repaying when long-term loans became explicit).
- Cross-DB ordering: `purchase_gear` debits the wallet first then grants gear (refund on grant failure); `settle_cast` writes games.db first then credits economy.db, returning `CastStatus.PAYOUT_DEFERRED` on payout failure (never rolled back). Settlement only via `settle_cast` / `purchase_gear`; views never import ORM models. `catch_log` denormalizes species fields so catalog retuning never rewrites history.

## Memory

- **The path is the privacy boundary** (#408, replacing the per-bullet `[src:...]` tag it removed). File-backed per-user markdown under `data/memories/<user_id>/`, keyed by user id (cross-server, shared with DMs). The consolidated tier is ONE FILE PER FACT, filed under the compartment allowed to read it: `global/` (safe anywhere, and where the user profile lives by definition), `g/<guild_id>/` (that guild only), `dm/` (the owner's own DMs). Reading for guild G is `global/` + `g/<G>/` — two path joins, no tag parser, no read-time content filter, no fail-closed rule. The other tiers are per-scope and unchanged: `detail.md` (append-only cold evidence, hard-capped at `DETAIL_FILE_MAX_BYTES`, oldest-trimmed), `raw.md` (phase-1 staging, deliberately still ONE file — it is staging, never injected, and splitting it would multiply job rows and cooldowns by the number of guilds), `tone.md` (short always-read tone note). `main.md`, `main.bak.md`, the `v1` header and the identity line are gone. Layout rationale in `store.py`'s docstring; the file format and the section vocabulary in `facts.py`; the write/age half in `deltas.py`. Do not move it into SQLite and do not add legacy-layout fallbacks.
- **Fact file** (`facts.py`): a `---` fenced header of single-line `key: value` pairs, then the body. Deliberately NOT YAML (pyyaml is only a transitive dep, and a hand-rolled reader cannot be talked into constructing objects). The model authors `summary` / `section` / `durability` / the body; code stamps `id`, `compartment`, `owner_id`, `owner_name`, `subject_id`, `node_type`, `created`, `last_confirmed`, `keys` and never shows them to it — provenance held by code instead of copied by a model is the whole point. `id` is minted by `mint_fact_id` from `sha256(compartment + summary)`, so it is deterministic, per-compartment unique (a cross-compartment id collision cannot happen and the reader never arbitrates one), and **never influenced by conversation content**, which is what makes path traversal structurally impossible. `compartment` is stored only so a hand-edited or half-migrated tree is *detectable*: the containing directory wins unconditionally and a mismatch is skipped with a `logfire.error`, because there is no safe way to guess which side is right. `keys` (the `normalized_key`s a fact distils from) is the retry-idempotency handle: a `create` whose keys overlap an existing fact becomes an `update` of it, so replaying a partly-applied batch cannot file a duplicate.
- **Sections** are ASCII keys rendered to Chinese headings per flavor (`section_headings`), so the structured schema stays English while the injected document stays Traditional Chinese, and the RENDERED shape is byte-compatible with what the reply prompts always got. That compatibility is load-bearing, not cosmetic: `allowlist_ids_from_server_memory` parses `## 成員稱呼` out of the rendered server document and four prompts tell the model to read that table. A `member_alias` fact carries `subject_id` (the member, distinct from `owner_id` = the scope) and the renderer appends its `[id: N]`, so the id can never be hallucinated onto the wrong row.
- **Consolidation emits deltas, not a whole file** (`{action, fact_id, section, durability, summary, text, from_keys, subject_id}`). `_consolidate_locked` fans one raw batch out over the scope's compartments inside ONE `scope_lock` + one semaphore permit, the whole run bounded by `MEMORY_CONSOLIDATE_TIMEOUT_SECONDS` and each call by `MEMORY_COMPARTMENT_TIMEOUT_SECONDS`, so the worst-case lock hold is what it was rather than multiplying by the compartment count. `partition_raw_entries` buckets the batch in CODE off the `- sharing:` / `- source:` fields (a `source_only` observation with no usable source goes to `dm/`, never `global/`); only compartments the batch actually routed evidence to run, `global` first so every later one can take its facts as a read-only `<global_reference>` and neither restate nor silently contradict them (with no global bucket that reference is read off disk instead). **Each call sees only the evidence routed to the compartment it writes** — that, not a prompt rule, is what makes "a guild-locked observation cannot reach `global/`" structural. Information flows global -> guild, never guild -> global. The raw batch retires only when EVERY compartment applied; a retry is safe because deltas are id-keyed upserts.
- **Rejection is for shape errors only.** The LLM call failing, or the net-delete cap (`deletes - creates > max(MAX_NET_FACT_DELETIONS_FLOOR, existing // 2)`, exempt on the regeneration path because replacing the whole set is what that path is for). Everything else sanitizes per delta — unknown section, malformed id, empty body, non-numeric `subject_id` all drop that one delta. This asymmetry is the rule, not a preference: a deterministic content check re-run against the same raw batch and the same existing facts produces the same output, so rejecting the batch is not a retry, it freezes the scope's memory permanently while burning a consolidation call every cooldown. `_rewrite_shrank_too_much` and the `v1`-header gate are gone.
- **Aging is code, not prompt prose**, now that `last_confirmed` is stamped (`sweep_stale_facts`, run after each applied batch): a `recent` fact expires `RECENT_CONTEXT_TTL_DAYS` after last confirmation; a `stable` fact is dropped once it falls `STABLE_FRESHNESS_WINDOW_DAYS` behind the freshest stable fact **in the same compartment** (per-compartment anchoring, so an active guild cannot age out the memory of one the user visits less often); `permanent` durability, the `permanent` SECTION (nothing couples the two, and `render_existing_facts` feeds a mismatched pairing back on every later update, so one slip would otherwise age out an enforced directive) and `member_alias` never age. The sweep runs over EVERY compartment after a successful fan-out, not just the ones this batch touched, or a guild the user stopped visiting would hand back its months-old `recent` facts. The `[~YYYY-MM]` / `[YYYY-MM-DD]` markers the model used to write are gone.
- **Size governor**: `read_memory_document` renders sections in order, newest first within a section, and stops at `MEMORY_INJECTION_MAX_CHARS` with an explicit truncation notice. It never deletes, which is what stops it fighting the next consolidation over facts it would immediately write back; `_report_injection_size` logs `warn` past `MEMORY_INJECTION_WARN_CHARS` and `error` past the cap. Calibrated against the live store (median ~800 B, p90 4.8 KB, max 25 KB), so it is a backstop that fires on nobody.
- **Read caching is not optional.** `resolve_user_memories` is synchronous and can carry 8 users per reply; one fact per file would otherwise be hundreds of opens on the event loop. `read_memory_document` is cached on `(scope, compartments, flavor, max_chars)` against a per-scope write generation that every `write_fact` / `delete_fact` / `delete_memory_files` bumps, so a repeat read costs zero syscalls. The counter is exact because every write goes through the store under `scope_lock`; editing the tree out of process while the bot runs is not supported (nor is it today, for `_cleared_at`).
- **Two-phase write** (`services/memory/`, fire-and-forget; must never add reply-path latency; LLM failures silently keep the previous state): phase-1 `MemoryExtractorAI.extract` after each QA reply (per-user in-flight de-dupe replays only the newest skipped turn) + a phase-1.5 evaluator, then deterministic gates (`_validated_draft` / `_is_accepted_observation`) reject casual mentions, hypotheticals, bot suggestions, other-user context, weak confidence, non-target observations, and duplicate `normalized_key`s before raw append. The `durability` ladder is `volatile|session|recent|stable|permanent`. Phase-2 runs once `RAW_CONSOLIDATION_THRESHOLD` accumulates and the cooldown elapses (`RAW_CONSOLIDATION_MAX_BYTES` bypasses cooldown), capped by `MEMORY_GLOBAL_CONCURRENCY`. Thresholds + reasons in `constants.py`. Models: `memory_extractor_model` for phase 1, `memory_writer_model` for both later gates (the phase-1.5 evaluator and phase-2 consolidation), split on the one seam worth tuning at.
- **The sharing gate is tighten-only, and code owns three of its four rules.** `_sanitize_observation` forces `source_only` on `recent_context`, on `evidence_kind="ongoing_situation"`, on an `[id: N]` / `<@N>` token naming anyone but the target, and on any observation whose text literally names another conversation participant. The roster comes from `participant_names_from_transcript`, read out of the transcript's own trusted author prefixes (so a resumed job rebuilds it with no extra DB column, and the bot — which has no author prefix — is absent by construction; a forged prefix can only ADD a name, and an extra name only tightens). Latin names match on a word boundary at 3+ chars, other scripts as a substring at 2+; a false positive keeps a harmless fact inside one guild, a false negative publishes a private one everywhere, and with no read-time filter left that asymmetry decides the rule. The fourth rule is the phase-1.5 evaluator's: naming or describing anyone but the target is `source_only` even with no id token. **Do not add a Chinese pronoun/relation lexicon** — it was measured against the live store and re-locks 14.5% of all `global` observations (`他` is a substring of `其他` and `吉他`).
- **Anti-injection** (plumbing in `extraction.py`, not `prompts.py`): the transcript renders column-0 `[message <n> | <role>]` markers with indented bodies so user text can't forge a boundary; `sanitize_identity` (`input.py`) neutralizes `[id:`-lookalikes in names; `redact_secrets` (`_SECRET_PATTERNS`, shape-specific, deliberately no bare-hex rule so git SHAs survive) runs on the transcript and every model output. Prompts treat conversation content as data, never instructions.
- **Read path is deterministic first, optional selector second.** Code always resolves the current author, resolved reply-chain authors and current-message explicit mentions in that order; `build_memory_allowlist` sanitizes and dedupes those trusted Discord users, then `resolve_user_memories` enforces both the per-user allowlist and the compartment boundary. `compartments_for_reading` decides how much of an allowed user's memory this conversation may open — guild G gets `global` + `g/G`, the owner's own 1:1 DM gets everything (their own information cannot leak to themselves), a third party inside a DM and a group DM get `global` alone. Only a public guild channel with additional ids in the rendered `## 成員稱呼` table starts `_select_user_memories`; its allowlist contains those absent alias owners only, its `MEMORY_SELECT_PROMPT` asks solely whether the latest message obliquely refers to one, and timeout/error loses only that optional memory. The selector gets the remaining slots under `MEMORY_CONTEXT_TARGET_USERS` but never displaces deterministic participants. Both sets merge into one low-authority `role=assistant` block (`render_memory_context_block`); `tone.md` remains author-only. **An allowlist entry is a `MemoryCandidate`, not one label**: `prompt_label` is what the model reads and carries the `## 成員稱呼` row appended when there is one, while `credit_label` is the short escaped `display (username)` the public usage footer names. Do not collapse them — the row is unbounded model-written prose free to describe a member in joke terms, and it used to land verbatim in the credit line (#463). A member the conversation knows only from that table carries no `credit_label`, so `resolve_user_memories` falls back to the identity their own facts stamped and then to the bare id; the guild member cache is not an option there, since without the members intent nextcord never caches a plain message author. That fallback reads through `compartments_for_reading`, NOT `read_owner`, which scans the whole scope: a stamped `owner_name` is `Member.display_name`, so it is the nickname of whichever guild's consolidation wrote it, and a member with nothing under `global/` would otherwise be credited in a public footer by the name they use in an unrelated server. It is uncached and costs a whole compartment read, bounded by being reached only by a selector-chosen member who has memory readable here. SUMMARY runs neither deterministic user-memory reads nor selection; IMAGE/VIDEO consume the speculative context. Pass a memory-free, target-centered `message_list` (`target_centered_memory_messages`) to extraction so it never re-ingests stored memory.
- **Restart-resumable phase-1 inbox** (`services/memory/database.py`, tables `memory_job` / `memory_token_clock` in `reply.db`): the markdown store stays the source of truth (do NOT move memory *content* into SQLite); this DB only persists the *progress* of the fire-and-forget pipeline so a redeploy mid-extraction is not lost. One row per scope, newest-wins under a logical integer token: each process reserves one range from SQLite above the persisted watermark and every legacy job token, then assigns turns and clears in capture order, so NTP rollback cannot make a clear older than the transcript it erases. `schedule_memory_update` renders the transcript eagerly and `_run_memory_update` writes `status='pending'` at its top; phase-1 terminal marks `done` (transcript nulled); an `extract()` LLM failure marks `failed` (transcript kept), so the restart sweep retries it with no timeout tuning; a user clear writes `cleared` (transcript, subject, identity and error scrubbed), a durable tombstone whose newer token rejects any pre-clear staging write that commits late. `ReplyGeneratorCogs.on_ready` (guarded by `_resume_started`, fires every reconnect) starts the git worker, re-enqueues only `pending` / `failed` rows and sweeps every over-threshold scope (`iter_scopes` + `consolidate_if_needed`), including scopes with a resumed job: the scope lock plus the under-lock `_should_consolidate` re-check keep the resumed extraction and the sweep idempotent. Consolidation itself needs no job rows since `raw.md` is its durable, re-entrant queue. Normal DB calls are best-effort (`_safe`, swallow + `logfire.warn`), the opposite of `cogs/research/cog.py`, so reply.db trouble never breaks the in-memory pipeline; the clear tombstone is the one deliberate exception because its commit carries the restart privacy guarantee.
- **Tone note (`tone.md`)**: persona-independent delivery preferences (the qualities the user wants, never a named persona or the current voice, so a `PERSONA_CHOICES` change never strands it) live in their own per-user tier, OUTSIDE the compartment tree — cross-server safe by construction, the deliberate exception to the boundary. It is therefore the one thing that must NOT be partitioned: ~48% of observations are `source_only`, so a note fed only the global bucket would stop updating for half of all conversations. That is why `_update_tone_note` is its **own** LLM call rather than a field on the `global` compartment's: it is handed the whole batch's tone-bearing observations (`tone_evidence_from_raw`, categories `interaction_style` / `stable_preference`) with NO `<existing_facts>` and NO `<raw_entries>`, and its `deltas` are discarded by code — so the unpartitioned input it needs can never become a stored fact. Folding it into the global call would have demoted the whole boundary back to a prompt rule. It is skipped entirely when the batch carries no tone signal (the normal case, and one fewer call). `_write_tone_result` accepts only user flavor + a `## 語氣偏好` header; an empty output never deletes the note, and only `_rebuild_tone_note` (the evidence-complete rebuild, which saw everything) may clear it. Injected for the message author on EVERY reply with no selection (`render_tone_block`, `ReplyContext.tone_block`, one file read, even on SUMMARY; media persona replies too); `PERSONA_CHOICES` says the note overrides the default voice, delivery only. `TONE_FILE_MAX_BYTES` is a store backstop, shortness lives in the prompt.
- `regenerate_main_memory` (`pipeline.py`) is the shared pure-evidence rebuild for `/memory regenerate` (default `memory_writer_model`, own `MEMORY_REGENERATION_COOLDOWN_SECONDS`), `scripts/regen_memories.py`, and `scripts/migrate_memories.py`: it rebuilds every compartment from the detail tail + unconsumed raw only, never the existing facts, and deletes what it did not re-emit. It is the ONE path allowed to lose most of a compartment at once (`allow_mass_delete=True`), which is also why the migration needs no migration-only writer. `/memory regenerate` dispatches a de-duped background task via `schedule_memory_regeneration` and replies immediately.
- **git history** (`git_history.py`, `MEMORY_GIT_ENABLED`): `data/memories` is a local repository, never pushed. A successful consolidation, rebuild or clear enqueues a commit of that ONE scope directory through a single worker behind one process-wide `LoopLocalLock` (`MEMORY_GLOBAL_CONCURRENCY` is 24 and `git commit` takes `.git/index.lock`, so unserialised commits fail exactly under load), and the worker takes that scope's `scope_lock` before staging because a delta batch is N renames, not one atomic replace, and a torn recovery point is worse than none. The `git status --porcelain` guard before `add` is required, not an optimization (`add` on a never-tracked, now-absent path exits 128). The bot never runs `git init`; a missing repository, or a run of failures, disables the service silently. `git` is in the Dockerfile because the base image has none, and the committer identity rides on every invocation (`-c user.name` / `-c user.email`) because the container runs as a user with no gitconfig and a container hostname carries no domain, so git rejects its own auto-detected ident and every commit exits 128 — both measured, and either one alone makes the feature a permanent production no-op. **A `/memory clear` commits the deletion but does not erase history** — earlier commits still reach the content, and pruning only drops unreachable objects. That is a recorded decision on #408 for a private single-operator store, and the user-facing wording is deliberately unchanged.
- All writes serialize under `scope_lock(scope)`; fact writes are atomic tmp + `os.replace`; in-flight updates check `cleared_since` so a clear isn't resurrected. Tests use the `memory_isolated_dir` fixture, which also resets the render cache + generation counter and disables the git service so no test can ever commit against the live store.
- `store.py` / `pipeline.py` are keyed by an opaque `scope: str` (the subdir under `data/memories/` and the registry key); `user_scope(user_id)` / `server_scope(server_id)` build it, and one store + one pipeline serve both flavors (shared `MEMORY_GLOBAL_CONCURRENCY`, per-scope de-dupe + cooldowns). **`scope` is the owner key and `compartment` is the visibility axis; they are never the same word.** `MemoryExtractorAI` carries its phase prompts as fields; `extract(subject, ...)` takes a per-call `target_user_id:` / `target_server_id:` subject.
- **Per-server (community) memory** at `data/memories/bot_memories/<server_id>/global/` (`BOT_MEMORY_DIR_NAME`, fixed and non-numeric so it is not confusable with a user scope on disk and survives a bot-account change) via the same store, the same delta protocol and the same reader, with `server_prompts.py` (sections 伺服器輪廓 / 社群文化 / 常見話題 / 重要事實 / 成員稱呼 / 近期脈絡). It has exactly ONE compartment because its observations carry no source or sharing to route by and a server memory is per-guild by construction — same code path, one hardcoded bucket, no second writer. `gen_reply` reads it once (`_read_server_memory`) and injects `render_server_memory_block` into both the selection request and the answer (zero extra latency), and schedules a server-scope update after each guild QA or SUMMARY. `## 成員稱呼` is the sole carve-out from the no-individuals rule, recorded with `durability=permanent` so the sweep never ages it. DMs skip both; SUMMARY skips user memory but still records server memory. The write side is gated by `_source_channel_is_public` so content a channel's `@everyone` can't view never feeds the member-readable server memory.
- User-facing commands read, rebuild, or erase the PERSONAL scope only: `/memory show`, `/memory regenerate`, `/memory clear`, plus the read-only `/memory server show` (community memory stays operator-maintained, so there is no server-side clear). `/memory show` renders one section per compartment, labelled with who can see it (`compartment_label`) — the information is structural now rather than an inferred tag, so showing the owner where each fact can resurface costs nothing. `/memory clear` opens a `MemoryClearConfirmView` and the button — never the command — calls the single orchestration point `pipeline.py::clear_scope_memory`, which opens a `mark_cleared` boundary, drops `_pending_updates[scope]`, and under a short per-scope `_staging_locks` lock writes a logical-token `cleared` tombstone through `clear_job`, removes the tree through `delete_memory_files`, then closes the boundary with `mark_cleared` in `finally`. **A clear is only whole if all four holdings are neutralized**: files are removed, the deferred replay is dropped, in-flight work sees the process stamp, and reply.db retains only the scope/flavor/token/timestamps needed for a transcript-free tombstone — never transcript, subject, identity or error text. `clear_job` is the ONE memory DB call deliberately not wrapped in best-effort `_safe`: it runs before any file is touched, so its failure leaves every durable tier in place; the file half can stop part way, so its failure embed points at an idempotent retry and neither failure rolls back the process stamp or dropped replay. Caller cancellation cannot interrupt that durable segment: `clear_scope_memory` shields and drains its owned critical task before propagating cancellation, while a critical DB failure is propagated instead of masquerading as a cancelled success. **A clear that erased anything records that it erased it** (#428): the `memory_git.enqueue` and the `logfire.info` audit line — the two traces the design keeps outside reply.db's own `cleared` row — are taken BEFORE the `CancelledError` is re-raised (the shielded task has already drained, so a cancelled clear erased just as much, and neither call awaits, so nothing interleaves), and the audit line carries `caller_cancelled` because that path is otherwise SILENT: the button defers before the clear starts and nextcord's dispatcher catches only `Exception`, so cancellation leaves the prompt never edited rather than showing Discord's "This interaction failed" (which #428's own text and the older `views.py` comment both claimed — measured against nextcord's `InteractionResponse.defer` and `View._scheduled_task`). `clear_job` RAISES against a row whose token is already newer than the clear rather than letting its guarded upsert no-op and returning False: that False let the caller delete the files with the pre-clear transcript still resumable in reply.db, which is #397 / #400 / #401's failure through a different door. Unreachable while one process owns the token block, so the guard exists to make a second writer against the same `reply.db` loud instead of silent. The clear deliberately does NOT take `scope_lock`, since that could wait minutes for consolidation. Every FILE write is immediately after `cleared_since` with no await in between. The reply.db staging path instead shares `_staging_locks`: a row that commits before clear is scrubbed by the newer tombstone token, and a turn captured during the clear waits for the closing stamp then writes nothing. A genuinely post-return turn receives a newer token and may replace the tombstone. This lock never spans extraction or consolidation. The process-exit, stale-token, partial-file-failure, completion-boundary, cancellation, unrecorded-erase and unwritable-tombstone regressions are covered by `test_clear_overwrites_a_staged_row_even_if_its_task_is_cancelled`, `test_a_row_write_racing_a_committed_clear_keeps_the_tombstone`, `test_clear_token_advances_past_legacy_wall_clock_tokens`, `test_clear_completion_drops_a_turn_staged_during_its_db_write`, `test_cancelled_clear_waiting_for_staging_lock_finishes_the_tombstone`, `test_cancelled_clear_still_records_that_it_erased`, and `test_clear_keeps_the_files_when_the_tombstone_cannot_be_written`; a test reading a DEFERRED turn's row must first drain `pipeline._db_tasks` through `_wait_for_persisted_writes`. Every turn uses `captured_at` from enqueue time, so a clear that lands while a turn is queued aborts it too. An offline wipe while the bot is stopped must also create a tombstone or remove that scope's row; an online clear must use this protocol because staging writers can still exist.

## Other Cogs

- `parse_threads/cog.py` watches `threads.net` / `threads.com` URLs (`THREADS_URL_RE` in `utils/threads.py`, shared with `gen_reply`) and uses reactions for status; no extra reward. Two path shapes name a post and the regex is anchored to both: the canonical `@user/post/<code>` and the `share/<code>` link the mobile share button copies. Only the first names its own post — a share code is unrelated to the post's (`DfX81RWN8` for a post whose code is `DZZImVsCWU-`) and appears nowhere in the page — so `ThreadsURL.post_code` is EMPTY for it by design, and `extract_post_data` takes the code from where the fetch landed (`FetchedPage.final_url`, free because `requests` already follows the 302), then points the empty-page retries at that canonical URL. What each post CARRIES is a separate question from what is fetched: `_build_conversation` reconstructs every post's `url` from its own author and code (`_post_url`), the target included, and the caller's URL survives only as the target's fallback and only through `clean_url`. That value is published (this cog's embeds and omitted-post notices, plus the permalink `gen_reply` quotes into the prompt) while both pasted shapes are minted per share, so echoing one names whoever sent the link to the channel: a `share/<code>` identifies the sharer directly, and the canonical URL its redirect answers with carries an `?xmt=` token that does the same. `test_the_target_url_never_carries_what_names_the_sharer` pins all three input shapes, and the share-link failure log logs `clean_url` for the same reason (the path is the whole signal there). Every fetch is aimed at `https://www.threads.com` (`_CANONICAL_THREADS_ORIGIN`, the one origin Threads answers without a redirect); the normalisation used to point at `www.threads.net` and each read silently paid a 301 back (#394, measured, pinned by `test_threads_url_clean_url_aims_at_the_host_that_answers`). Do not go back to reading the code as the URL's last path segment: it would hand the parser the share code, which no post on the page carries, and an empty code matches any post payload serialised without one, which is why a share link that lands on a non-post URL returns an empty page instead of being parsed. A reply URL expands the whole reply chain into one message and `_build_embeds` fills the 10-embed cap by RESERVING one slot for the target's own words and one for the post it quotes before any image competes, then spending the rest on images target-first, quoted next, then up the chain (comments have the budget detail). Both reservations are load-bearing: a quote post is typically one line over someone else's ten-image carousel, and an image-first pass hands the whole cap to that carousel and drops the commentary that owns the message. No media-count guard on purpose: an oversized carousel degrades to its first images rather than refusing the post; the 4096-char guard stays but now measures the RENDERED embed descriptions rather than `target.text`, since the quoted-post marker prefix and the video / unavailable hints are appended after any check on the raw body and turned a ⚠️ skip into a Discord 400. Discord applies a SECOND, message-wide 6000-character budget across every text-bearing field of every embed, so `_select_posts_within_text_limit` drops WHOLE posts in the same relevance order the slots use (the target is never dropped) before `_allocate_embed_slots` runs — a per-embed guard alone still 400s a chain of ten in-limit posts. Both guards count UTF-16 code units (`_utf16_length`), conservative for astral-plane emoji since Discord leaves "character" unspecified. What the two passes shed is not silently lost: `_collect_omitted_posts` gathers the chain-trim overflow plus every unslotted post and `_omitted_post_notice_pages` posts their permalinks as follow-up replies, paginated under the 2000-char message cap. That notice is strictly additive and cannot cost what it reports on (#426): it never raises (a line no page could hold is handed to the closing count instead), it is capped at `_MAX_OMITTED_NOTICE_PAGES` with the remainder stated as a count rather than emitted as more replies, and `_post_omitted_notices` runs AFTER the expansion's reply and after ✅, behind its own broad `except` — so a notice failure can neither abort a rendered expansion nor relabel a delivered one ❌. This cog walks the whole chain (`MAX_THREADS_POSTS` is gen_reply's cap, not its own), which is why the page ceiling has to exist here. The old `total_size` byte guard is gone (oversize videos are hosted as URLs via `MediaDeliveryPlanner.plan`, and the whole post is refused only when they cannot be hosted, via `plan.dropped_items`). This cog downloads the target video to disk for its embeds (`parse`, a context manager over the SAME walk as `parse_metadata` — both return a `ThreadsConversation`, and downloading the target's video is the only difference left between them); it reads `.chain` plus the target's `.quoted` and deliberately shows no comments, since the 10-embed cap has no room for them. A quoted post's media stays URL-only in BOTH walks (images cost nothing as `set_image(url=...)`, a quoted clip takes the ancestor `🎬 [點此觀看影片]` link-hint precedent), which is also what keeps `parse` and `parse_metadata` producing equal trees; an unavailable quoted post appends a line to the TARGET's embed only (`is_target`-gated, since the expansion shows no ancestor's quote at all) rather than spending a slot on a tombstone that carries neither username nor shortcode. `gen_reply` runs `parse_metadata` and fetches only the target's media and the quoted post's. The two never both fire on one message: a message addressed to the bot is skipped here (see the mention rule under Routes). They can fire on one *link* across two messages, once this cog expands it and again when someone replies to that message and mentions the bot — that reply is asking for the comments this cog has no embed budget to show. It cannot be triggered by replying to the expansion itself; `_authored_link_texts` (under Routes) has the why, and `_build_embeds`'s root-first order is the reason.
- `parse_douyin/cog.py` watches Douyin URLs (`DOUYIN_URL_RE` in `utils/douyin.py`, shared with `gen_reply`) and mirrors `parse_threads`: reactions for status, a per-invocation `tempfile.TemporaryDirectory` (filenames derive from the post id, so a shared dir lets two expansions truncate each other), `MediaDeliveryPlanner.plan` for attach-vs-host, `result.total_bytes` read BEFORE `plan` (hosting moves the file out). Auto-expansion is justified for Douyin specifically (a pasted link means "watch this", unlike the many platforms `/download_video` serves) and kill-switched by `DouyinConfig.auto_expand_enabled` — the one lever that stops the bot contacting Douyin during a WAF incident. Request volume is the binding constraint, so `utils/douyin.py` holds a per-URL `KeyedLockManager` plus a small `LoopLocalSemaphore` shared with `gen_reply`'s builder, alongside the module-level payload and short-link caches. `DouyinBlockedError` gets its own ⏱️ reaction and wording: reporting a WAF block as a deleted post is the worst outcome the feature can produce, and `douyin_failure_message` is the single mapping (`video/cog.py` uses it too). `_download_to`'s `max_bytes` is a fail-fast guard read off `Content-Length`, not a policy: `/download_video` and the cog pass `None` (an oversize file is the media host's job), while the AI path passes only the Files API's 2 GB ceiling.

It owns the module-level `_sql_engine`; do not move it to a `cached_property` (per-message would leak the pool / dialect / inspector cache, see the comment).
- `feedback/cog.py` + `cogs/feedback/`: `/feedback` opens an ephemeral panel of the caller's own reports and files new ones as issues on `FEEDBACK_GITHUB_REPOSITORY` (REST over `httpx`, no `gh` CLI in the image and no MCP server at runtime). **The ordering is the design**: the row is written to `feedback.db` first, then the issue is opened FROM THE RAW TEXT, then the reporter is answered, and only then does a background `slow_model` write-up rewrite the issue. After the local write nothing external can lose a report (`retry_unfiled_reports` finishes the hand-off, skipping rows younger than `RETRY_MIN_AGE_SECONDS` because a submit mid-flight is indistinguishable from a failed one), and because the issue starts as the reporter's own words a failed write-up needs no fallback text. `attach_issue_number` is conditional on the column still being empty so the two writers cannot overwrite the number the reporter was already given. There is deliberately **no admin surface**: replies are written on the issue, and status is derived per panel open (open + no maintainer comment = 還沒回覆, open + one = 處理中, closed + `state_reason`) rather than stored, so it cannot drift. Only OWNER / MEMBER / COLLABORATOR comments are shown and bots are dropped — the repo is public, and relaying a stranger as the developer is the worst failure available here — while a reply relayed FROM the panel is posted with the bot's own token and so comes back as a maintainer comment unless marked (`REPORTER_COMMENT_MARKER`), which is also why `relayed_replies` is counted locally. An unreadable conversation stays `None` and says so instead of rendering as "nobody replied". The reporter's verbatim text always rides in the issue inside a fence longer than any backtick run in it, which is what keeps `@name` and `#123` inert. The owner is DM'd on a new report because GitHub does not notify you about issues you opened yourself. A missing token is an operational state, not a switch (`FeedbackConfig.github_ready` vs `enabled`): the panel still opens and reports still queue, and the first sweep after the credentials land files all of them, so a deployment mid-setup does not throw away the reports it gets on day one. The write-up does not wait for a token either — two of its four fields are local (the panel's own summary line and the classification), so a queued report is tidied on arrival and `_open_issue` then opens its issue from `stored_draft` in one call instead of opening it raw and editing it. Authentication is a swappable credential (`auth.py`): a GitHub App signs a JWT with its PEM and exchanges it for an hour-long installation token (installation id looked up, not configured), or an account token is used as-is; the app is preferred because it files issues under its own name and because GitHub does not notify you about issues you opened yourself. Switching to an app is what forced `select_conversation` to check the reporter marker BEFORE the bot filter — an app comments as a `Bot`, so the old order silently dropped every reply a reporter relayed through the panel — and the marker is only honoured on a comment that is ours (bot or maintainer), or anyone could paste it and have their words shown back to the reporter as the reporter's own. Env is `FEEDBACK_*`-prefixed on purpose: Actions exports `GITHUB_REPOSITORY` and `gh` users export `GITHUB_TOKEN`, and `load_dotenv` does not override those.
- `media_cleanup/cog.py` runs the hosted-media size/age/temp sweep (`MediaHostingService.run_maintenance`) on a `@tasks.loop` plus once at startup, gated by a `_started` bool on `on_ready` (mirrors games/research) and self-disabling when `cleanup_enabled` is false; publishes enforce the size cap eagerly, so this is the backstop. Never let its sweep run in a test (it deletes against the env-resolved live serve dir) — test the gate only.
- **Usage records** (#429, `utils/usage_log.py` + `usage/cog.py`): one JSON line per slash invocation and per AI reply in `data/usage/<YYYY-MM>.jsonl`, so an operator stocktake can find the features nobody uses. Deliberately NOT in `data/logs` — that file is debug-level, hand-cleaned and gated on `LOG_LEVEL`, so a usage history there dies with it or silently stops. The slash listener is on `on_interaction`, NOT `on_application_command_completion`: the gateway dispatches `interaction` for every INTERACTION_CREATE (`nextcord/state.py`) before `process_application_commands` runs a check or callback, so it alone sees a rejected, unresolvable or raising invocation — someone pressing the button is the demand signal, and it must not be lost because the command is broken. It has to be a **cog listener**; overriding `on_interaction` on `DiscordBot` would replace `Client.on_interaction` and stop slash commands executing entirely. `interaction.application_command` is unset that early, so `command_path` walks the payload's own option tree for the full path (`memory server show`), keeping a subcommand its own unit. The reply record is written from `_run_reply_pipeline`'s `finally` — the one scope holding both the route and the outcome — as one record per triggering message (not per delivered artifact), named `unrouted` when the failure preceded the router; the empty-prompt `?` path records nothing (no model ran) and deep research is left to `reply.db`'s own `research` rows. **No success/failure field on either kind**, by design: these answer "someone used this", the runtime log answers how it went, and carrying an outcome would force the slash record off the only point that sees every invocation. Records hold numeric ids only — no names, no content, no arguments — since nothing prunes these files. Writes are best-effort (a failure is a `logfire.warn`, never raised into the recorded feature) and `USAGE_LOG_ENABLED=false` makes the recorder inert. The autouse `usage_log_isolated_dir` fixture points every recorder a test builds at a `tmp_path`; a cog built via `__new__` (`tests/test_gen_reply.py::_cog`) must be handed one explicitly.

## Conventions

- Environment-backed config classes use `pydantic_settings.BaseSettings` with explicit `validation_alias=AliasChoices("ENV_NAME")`; `.env` is loaded at import time.
- Pure shared result types, enums, and constants live under `typings/` when they don't depend on cogs or utils.
- Use `pydantic.BaseModel` for structured data and type-managed payloads, including service/helper classes. No `dataclass`; no loose `object` / `Any`. Keep `Field(description=..., examples=...)` on every model; a required field uses an explicit ellipsis: `Field(..., description=...)`.
- Log severity follows the ladder in `.github/CONTRIBUTING.md#logging`, keyed on how tolerable the failure is, not on how deep it happened: a routine user-driven outcome (deleted message, private post, WAF block, kill-switch skip) is `info`, a handled degrade is `warn`, and `error` is reserved for an unexpected failure that lost a deliverable or left state inconsistent. Every log inside an `except` carries the exception, and a broad `except` that stays broad says why in a comment. `LOG_LEVEL` (default `debug`) sets the console + `data/logs` floor.
- Ruff is formatter and linter; `ty` is the only type checker (configured in `pyproject.toml`). mypy was removed in #356: its pre-commit hook resolved no `discordbot.*` import, so every project type was `Any` and it reported success on a tree it never checked. Use narrow `# noqa: <rule>` comments with a reason.
- `ty` types a pydantic field annotated with an arbitrary class (anything pydantic cannot model itself: `nextcord.Message`, `genai.Client`, `AsyncOpenAI`) as `Any` in the `__init__` it synthesizes, so those constructor arguments are unchecked at every call site; annotations pydantic does model keep a real type (`int` becomes `LaxInt`). The `SkipValidation[T]` wrapper is irrelevant to this — the signature is identical without it, and dropping it only changes runtime validation. Since #356 there is no second checker, so a wrong handle handed to one of `gen_reply/`'s services surfaces at runtime.
- Keyword arguments are required for normal calls, including single-argument ones; do not add bare `*`. Allowed positional idioms: `len(x)`, `str(x)`, `Path("x")`, exception constructors, variadic collectors, `logfire.info("message")`.
- Avoid intermediate one-level aliases such as `usage = responses.usage`.
- Import functions by name and call them unqualified (`from pkg.mod import do_thing`); a module-namespace import is a last resort with a reason.
- An `asyncio.Lock` / `Semaphore` / loop-bound registry must not outlive one event loop, module-level or on a process-wide singleton: each test runs on a fresh loop, and the primitive binds to the loop of the first call that actually waits on it (not at construction, so building it lazily does not help), then raises `is bound to a different event loop` there. Use `utils/asyncio_locks.py` (`LoopLocalLock` / `LoopLocalSemaphore` / `LoopLocalRegistry` / `KeyedLockManager`), which rebuild on a loop change.
- LLM latency matters; do not add extra LLM calls for cosmetic improvements.
- `docs/` is generated by `make gen-docs`; do not hand-edit it. Do not touch the README badge block unless explicitly asked.
