# CLAUDE.md

Project-specific guidance for Claude Code in this repository. Dense and AI-agent-facing on purpose: an index of pointers, cross-cutting invariants, and non-obvious pitfalls, not a re-explanation of what the code already documents. When a fact already lives in a code comment or docstring, this file keeps only the pointer plus the load-bearing "why".

## Commands

All tooling runs through `uv`.

```bash
uv run discordbot                # run the bot
uv run pytest                    # tests, coverage gate: 80% (--cov-fail-under)
uv run pytest <path> --no-cov    # focused run; without --no-cov a subset exits 1 on that gate
uvx pre-commit run -a            # canonical pre-push check (= make fmt)
uvx pre-commit run ty -a         # type check alone; `uvx ty check` rejects --all-groups (a uv flag)
make gen-docs                    # regenerate docs/ from sources
```

Config comes from `.env` (see `.env.example`): `DISCORD_BOT_TOKEN` + `OPENAI_BASE_URL` / `OPENAI_API_KEY` are the minimum to boot and `GEMINI_API_KEY` unlocks every direct-to-Google path; the rest are the kill-switches, `MEDIA_HOSTING_*`, `FEEDBACK_*` (a GitHub App id and a PEM path among them), `MEMORY_GIT_ENABLED`, `USAGE_LOG_*` and `LOG_LEVEL`.

When debugging, check `./data/logs` for the full runtime logs.

Tests share their isolation in `tests/conftest.py` and their scaffolding in `tests/helpers/` (`discord_mocks.py` fakes an Interaction / Message / followup; `llm_input.py` pulls a named block back out of a recorded Responses request). Reach for those before writing a new fake. Four fixtures are AUTOUSE and easy to miss — `usage_log_isolated_dir`, `file_api_enabled_by_default`, `model_price_mirror_isolated` and `feedback_env_isolated` — three of them because a real deployment's `.env` would otherwise decide a test's outcome. Unit tests must inject fake LLM clients and extractors and pass without runtime API credentials; the Tests workflow intentionally provides none.

## Runtime Shape

- `src/discordbot/cli.py` defines `DiscordBot(commands.Bot)`; intents are `Intents.all()` minus `members` and `presences`.
- Cogs load synchronously in `__init__` before the gateway connects. Every cog module exposes a sync `def setup(bot)` and adds the cog with `override=True`; an `async def setup` breaks the first command sync, and `_load_cogs_sync`'s docstring has that mechanism end to end.
- **A cog is a directory holding `__init__.py` and `cog.py`** (#403); `_load_cogs_sync` scans `cogs/` one level deep, skips `_`-prefixed entries (which is what keeps `__pycache__` out of it), and raises on anything else that is not a cog rather than skipping it, so a half-finished move cannot silently drop one. Its docstring has why the scan is one level. `cogs/<name>/__init__.py` carries no re-exports (a docstring is fine): a re-exporting one would make `from discordbot.cogs.economy.database import x` execute the whole cog body as a side effect of initialising the package. Nothing in the tree enforces that but this line.
- **`services/` is the layer below the cogs** (#403): a domain engine two or more cogs need, plus whatever that engine itself needs. `services/economy/` is the ledger every money-moving feature writes through, and `services/memory/` the store `gen_reply` writes and the memory cog reads. It is Discord-free and never imports from `cogs/`. Below it, `utils/` and `typings/` carry no domain state and import from neither. A module belongs in `services/` when it is part of the engine itself: a second cog needs it, an engine already there needs it, or it is that engine's own vocabulary — `services/memory/server_prompts.py` has exactly one caller (`gen_reply/cog.py`) and still belongs beside `services/memory/prompts.py` rather than splitting one prompt vocabulary across two layers. Anything else stays inside the one cog directory that uses it.
- The trade this makes is deliberate: a feature that has both a Discord surface and an engine (economy, memory) lives in two paths, split on that seam. Every other cog is one directory.
- Bot presence is hardcoded in `status_task`; there is no DB-backed rotation.
- Add common command errors in `DiscordBot.on_command_error`, not in each cog.

## Cog Rules

- **A user-facing surface is designed in an artifact before it is built.** A panel, a view, a modal, an embed layout or a rendered PNG board is settled by publishing a mockup and reviewing THAT: Discord-faithful chrome, both themes, real copy, and every screen the flow reaches rather than the first one. It catches what prose hides — a status that reads as decoration, a field order that buries the thing the panel exists to track, a control whose scope nobody agreed — and moving a field in HTML costs minutes where moving it in a shipped cog costs a rewrite plus everyone's muscle memory. Put the open design questions on the same page, each with a recommendation, so the answer comes back as a decision instead of a re-derivation. Wording-only work (a command description, one failure line) needs none of this.
- A `nextcord.ui.View` button/select callback must not be named after anything on `View` itself (`refresh`, `stop`, `children`, ...): `View.__init__` runs `setattr(self, func.__name__, item)`, so the name is rebound to the `Button` and the base method is gone. `tests/test_view_callbacks.py` has the concrete gateway breakage and walks every `View` subclass in the package. No type checker catches it — the decorator retypes the override to a `Callable` alias, which suppresses the override rule — which is why that test has to exist at all.
- One `commands.Cog` subclass plus a sync `setup` per `cog.py`. **Nothing under `cogs/<a>/` may import from `cogs/<b>/`** — not the cog module, not a helper. Reach across via the bot instance, `typings/`, `utils/`, or `services/`; `tests/test_package_layering.py` fails on a new edge, and its docstrings carry what the scan reads and the traps it was written for.
- User-facing slash commands need localized name and description for English, `Locale.zh_TW`, and `Locale.ja`.
- A slash option's type comes from its annotation, and nextcord reads `Literal[...]` (turning the members into choices, which an explicit `choices=` then overrides) but rejects an arbitrary `StrEnum` subclass outright, so a shared option vocabulary is a `Literal`: `typings/video.py::VideoQuality` carries the rule and the three sites a new preset has to be answered in. `SlashOption(default=...)` is deliberately typed `Any` upstream, making the default the one spelling `ty` cannot check; `tests/test_download.py` reads it off the registered command instead. `nextcord.SlashOption` sits in ruff's `flake8-bugbear.extend-immutable-calls` for the reason `pyproject.toml` gives beside it.
- Any user-visible command or behavior change must update `gen_reply/capabilities.md` in the same change and keep `tests/test_capabilities.py` green. That guard is what the deleted `/help` cog left behind, and it matters more now, since that document is the ONLY description of any feature anywhere: a command missing from it is a command nobody, the answer model included, can find. It runs both ways — every runnable path must appear in the document (which is how subcommands went undocumented before #378), and every `/command` the document names must be a runnable path or a group node (#433), so a rename cannot satisfy the forward scan under the new name while leaving the old line behind for the answer model to recite in the asker's own language. A command MUST therefore be written as a code span of its own. The test's own docstrings carry the scan mechanics plus five obligations beyond them: an admin-gated command states its gate on its own line, a loan command names its decider and its expiry, `/admin collect_tax` says it never goes below zero, no cog declares `default_member_permissions`, and no slash description names an admin without saying which. Neither direction reaches an inline marker, since it is asked for in plain language and the document describes it that way too; `markers.py`'s tag set is pinned in the same test instead, so adding or dropping one fails until the document says what the bot can now do or stops claiming what it no longer can.
- For aligned-width embeds use `utils.discord_embeds.embed_spacer_payload(..., target=)` so an edit reuses the uploaded spacer; re-uploading it every edit trips Discord error 400009 on rapidly edited messages (see its docstring).
- Content past embed limits is paginated or rendered to a PNG via `attachment://...`; never truncate silently.
- Never hardcode a Discord attachment-size ceiling: read the destination's real limit through the shared `utils/media_delivery.py::upload_limit_for(guild=...)`, whose docstring has the boost-tier lookup and the 20 MiB no-guild fallback. What it does not say is that the lookup is knowingly wrong for unboosted guilds: `filesize_limit` is nextcord's static `premium_tier` table rather than a live field, so it over-reports 25 MiB for tier 0/1 (Discord's real base is 20 MiB since 2026-08-13, after two years at 10 MiB), and the guild path keeps trusting it deliberately, so it self-corrects when nextcord refreshes its table. `MEDIA_ENVELOPE_MARGIN` (1 MiB) is held back by `MediaDeliveryPlanner.plan` for a combined edit or an attach riding with embeds. Call sites: `parse_threads/cog.py`, `parse_douyin/cog.py` / `video/cog.py` (envelope margin only for a multi-image gallery), `gen_reply/streaming.py`, `gen_reply/cog.py`, `research/delivery.py`.
- **Oversize → URL fallback / unified delivery** (`utils/media_delivery.py`): the attach-vs-host-vs-drop *decision* is unified in `MediaDeliveryPlanner.plan`, which returns a `MediaPlan` (`native` attachments / `hosted_urls` / `dropped_items`). Each feature stays pure — it produces `MediaItem`s and hands a list to `plan` — while the actual Discord send and the per-site degradation policy stay local, because the sends are structurally disjoint and unifying them buys nothing. The module owns the rest: content-addressed names and the atomic write, the allowlisted suffixes mirroring nginx, the self-cleaning serve dir with its size / age / temp sweeps, the reaper's own-files-only pattern, and why the bot never creates the serve dir. Three things it does not say. `MEDIA_HOSTING_ENABLED=false` (or no serve dir) must stay byte-for-byte the host-free path at EVERY call site — a standing invariant, not a local choice. `video/cog.py` dropped its 480p-downgrade retry when this landed, and a deleted behaviour leaves no trace in code. And the wiring is: the IMAGE/VIDEO routes (`gen_reply._deliver_generated_media`, where an oversize item posts a standalone URL message so the persona stream never clobbers it, while an unhostable one still raises to keep the route's hard-fail path), the QA streamer (oversized voice / music / inline image / inline video), `video/cog.py`, `parse_threads/cog.py` (per-item and mixed: it hosts only the oversize videos and attaches the rest), and `research/delivery.py`.

## AI Pipeline

### Backend and invariants

- Runtime LLM backend is LiteLLM Proxy behind `OPENAI_BASE_URL`; all runtime conversations use `AsyncOpenAI` and the OpenAI Responses API. Do not switch back to Chat Completions; do not import provider-native SDKs (`google-genai`, `anthropic`, `xai-sdk`) into request paths. The proxy indirection is the point: one OpenAI SDK for the whole project while the backend stays mostly Gemini and any model is hot-swappable via the model string. (`extra_body` is an affordance the proxy offers, not a mechanism anything uses — see the mock-testing gotcha below.)
- **Non-proxied paths** are the only runtime calls direct to Google, and they forgo proxy-side cost/usage tracking: Gemini Files API attachment upload (`gen_reply/attachment/gemini_file_api.py`) and the linked-post media upload that shares its rationale (`gen_reply/files_api.py`), the YouTube Interactions answer turn (`gen_reply/interactions.py`), omni video generation / editing (`VideoGenerator`, for BOTH the VIDEO route and the inline `<generate-video>` marker), the inline `<generate-music>` Lyria render (`MusicGenerator`), and deep-research agents (`cogs/research/`). THREE `cached_property` clients serve all of them (`gen_reply/cog.py`, `attachment/gemini_file_api.py`, `research/cog.py`), each building `genai.Client(api_key=gemini_api_key)` inline; there is no `create_*_client` factory left, and `utils/llm.py` stays as the shared *call* surface rather than a client one.
- On every direct-to-Google path the genai SDK entry point is `interactions.create`; `generate_content` is being deprecated upstream and has zero call sites here, so this is a keep-it-that-way rule rather than a pending migration. Do not reintroduce it, and do not fold its behavior into a measurement of what the native API can do: the two surfaces carry genuinely different capability gates (see Responses API Gotchas for the built-in-plus-function tool case), so a result from one does not transfer to the other. Read the `gemini-interactions-api` skill before writing one: it owns the call shape itself (input parts, streaming, background tasks, function calling, structured output, image / video generation) and it only loads if something makes it, so this line is what tells you to.
- A `google.genai` interaction result cannot be read straight off `interactions.create()`: it returns `Interaction | AsyncStream[...]`, and excluding the stream with `isinstance(x, AsyncIterator)` does NOT clear it, because genai's `AsyncStream` is only structurally an `AsyncIterator` and so stays in the union, leaving every attribute read an `unresolved-attribute`. Declare the attributes actually read as a Protocol and cast to that, as `generation.py::_InteractionResult` does; its docstring has the second trap — the star-import collision that makes a nominal `cast("Interaction", ...)` fragile rather than wrong, and why no checker in the tree will surface it again.
- Runtime model strings live in `RuntimeModelCatalog` (`typings/models.py`); each property's docstring carries its callers and tier rationale, and `models.py` owns why `none` / `disable` is never legal on the Gemini tiers it ships along with why `slow_model` is pinned to explicit snapshots and why its peak-hour branch answers off the flash family the off-peak one stays on. The three conversational tiers split on whether the output's shape is already fixed: `triage_model` fills a slot with no room in it (two enums, a list of ids, a thread title), `fast_model` composes prose short of the answer, `slow_model` writes the answer. That is the effort ladder too, since filling a slot needs no thinking. `tests/test_runtime_models.py` guards every tier against a `*-latest` alias, and every `slow_model` branch additionally against an effort other than `high`, sweeping each hour of a week rather than sampling the branches live today (a branch added on a second dispatch condition is otherwise invisible to it), and deliberately names no snapshot, so repointing that tier stays a one-line change (#498). **Which efforts a model accepts is looked up, never written down.** The set is per-model, and the vocabulary is per-provider, so it is not derivable from a name, a family, or a sibling snapshot and a guess is not even wrong in a consistent direction: Gemini has `minimal` and no `xhigh`, OpenAI has `xhigh` and on some models `none`, Anthropic has `max`. Nothing is universal — of the 138 reasoning models openrouter lists, `high` is on 134 and `low` on 110 — so do not trust any list of accepted efforts in this repo, in a comment, or in your own memory; every one of them goes stale the day a tier is repointed. Look the model up under its `<provider>/<name>` id in `https://openrouter.ai/api/v1/models`, where `reasoning` carries `supported_efforts`, `default_effort` and `mandatory` (whether thinking can be switched off at all). Not `supported_parameters`, which only says whether `reasoning_effort` is accepted as a parameter and lists no values. A provider's own docs are the cross-check where they publish one; Google's thinking page currently matches openrouter exactly. Do that lookup before repointing a tier, before widening `EffortGrade`, and before dispatching an existing tier down a new path. Two things the lookup does not tell you and that cost whole replies. Sending an effort outside a model's set is a hard failure rather than a downgrade, and on the direct-to-Google paths it surfaces as exactly that (#459); but through the PROXY it does not surface as an error at all — LiteLLM forwards the level for the model to refuse and then answers from the fallback deployment, so the caller sees an HTTP 200 whose `model` field names a different model, and a status code proves nothing here while only the response's own `model` does. That is also why a tier can look healthy for months and fail the first time a feature dispatches it direct to Google.
- Author runtime prompts in English (`prompts.py` / `server_prompts.py`, tool descriptions, routing/memory/voice prompts, `TTS_STYLE_DIRECTIVE`); reply *content* is localized at runtime by the in-prompt "follow the user's language" rule, not by writing the prompt in another language. Deliberate exceptions: the few load-bearing Chinese behavior notes in `COMMON_PROMPT` (e.g. the 轉帳 caution); the bot's own name 破貓.
- **Generated media style defaults**: IMAGE and VIDEO deliberately carry NO default aesthetic, visual style being left entirely to the model; only MUSIC and VOICE keep a deployment default, and VIDEO additionally keeps a spoken-language order. Each of those lives on the prompt or directive it steers (`prompts.py`, `generation.py`), with its own measurement. Do not reintroduce a code-side static style suffix for image/video: it can't honor "unless the user specified".
- LLM SDK objects are named `responses`; loop items are named `response`.
- LiteLLM's docs lag its code — answer proxy-behavior questions (request translation, `extra_body`, tool/grounding quirks) from its source, not its docs. `~/repo/litellm/` carries no library source: it is the proxy's deployment config, useful for which models and settings are live and which image the proxy pins. The source itself arrives transitively via `openai-agents[litellm]`, so read it in the uv env (`uv run python -c "import litellm, os; print(os.path.dirname(litellm.__file__))"`, version in `uv.lock`); when the answer depends on a version this env does not have, shallow-clone upstream into a scratch dir and read that instead. The uv copy is for reading; the authority on runtime behavior is the running container, which can drift from it, so confirm with `docker exec litellm-litellm-1 python -c "import importlib.metadata as m; print(m.version('litellm'))"` and read its source under `/app/.venv/lib/python3.13/site-packages/litellm`.

### Reply pipeline (`gen_reply` orchestration)

- **Dual render from one history walk**: `_fetch_history` does the single channel-history read. `_get_reference_and_current(text_only=True)` feeds routing and, only when an optional alias candidate exists, the narrowed memory selector; the uploaded-`file_id` render is awaited only by the answer, so the route never blocks on the Files API and a selector that actually runs still overlaps the upload window. Those four functions' docstrings carry the split.
- **Route is two parallel calls under one `route_done` gate**: `_route_classify` returns `RouteClassification` (only critical-path call, gates dispatch); `_grade_effort` returns `EffortGrade` concurrently. QA/SUMMARY override the slow model's effort with the grade (footer shows `model (effort)`); IMAGE/VIDEO cancel the effort task. **The grade is binary and `high` is the standing one** (#490), and **every message is graded by the model, blind spots included** — `_grade_effort`'s docstring has the #491/#493 measurements, and `input.py` the `[attachment: sticker]` marker that fixed the one case they found. Two rules the code does not state: do not reintroduce a code-side grade (the deleted predicate was `_hides_content_from_the_grader`, and `[attachment: image]` on a real image IS the honest marker), and the linked-post and channel-history blind spots are left to the prompt on purpose, since they are exactly the messages that ask for a real answer. Optional memory selection + effort grading share the `route_done`-gated `_await_gated` helper (unbounded while the route runs, then only a grace: `MEMORY_SELECT_GRACE_SECONDS` / `EFFORT_GRACE_SECONDS`). On timeout/error effort falls back to `high`; memory selection keeps the code-resolved author / reply-chain / explicit-mention memories and omits only the optional third party.
- **Speculative `ReplyContext`** (`_prepare_reply_context`): history + server memory + deterministic participant memory + optional alias selection built concurrently with the route. IMAGE/VIDEO consume it (not cancel) — awaited only after the media is on screen so its build overlaps generation; the reply injects `memory_block` but never `server_memory_block`. The author's `tone_block` is read unconditionally and rides every route. SUMMARY rebuilds at `history_limit=200`, `memory_enabled=False`, reusing shared parts.
- **Streaming UX** (`streaming.py`): progress is reactions on the user's message (`ReactionStatusChain`, ordered, fire-and-forget, custom app emojis); no separate status messages. `ResponseStreamer` previews the reasoning summary as `-#` subtext, replaced by the first content delta. Edits run on a snapshot editor task that shuts down via a stop-event rather than cancellation, and `_reply_or_send` degrades `message.reply` to `channel.send` on a deleted source; both carry their own why.
- **Best-effort convention**: a voice / inline-image / inline-music / inline-video failure leaves the primary deliverable plus a ⏱️/⚠️ react hint on the source, never raising into the pipeline's outer error path. That hint is the STREAMER's alone — an IMAGE or VIDEO persona-reply failure is silent to the user and only logs. Oversize is handled first by hosting the item as a URL (the decision lives in `utils/media_delivery.py`; see the oversize → URL fallback in Cog Rules), but only the streamer degrades an unhostable one to the drop + ⚠️ hint: `_deliver_generated_media` retries the native attach and lets it raise onto the route's hard-fail path.
- **Kill-switches** (`LLMConfig`, runtime; off still strips any marker but produces nothing): `youtube_video_enabled`, `deep_research_enabled`, `inline_voice_enabled`, `inline_image_enabled`, `inline_music_enabled`, `inline_video_enabled`, `douyin_video_enabled`, `bilibili_video_enabled`, `image_refine_prompt_enabled`, `video_refine_prompt_enabled` and `file_api_enabled` — exactly eleven, each with its own off-behaviour and Gemini-key requirement stated in `typings/llm.py`. `DouyinConfig.auto_expand_enabled` lives in `typings/douyin.py` instead, since auto-expansion is not an LLM feature. The two refine switches are the odd ones out: they gate a `PromptGenerator.refine` step per route rather than a marker, so off sends the raw request straight to the model. `file_api_enabled` is the operational one — it gates no feature but the mechanism under several, for a provider outage where the upload succeeds and the model is then refused the file (measured 2026-08-14 against Google, every model but `gemini-3-flash-preview`), which costs the WHOLE reply since the answer carries the failing part.
- **Logfire spans**, every one prefixed `gen_reply `: `pipeline` / `route` / `effort` / `context build` / `memory selection` / `answer` (carries a `backend` attr) / `prompt refine` / `image reply` / `video reply` / `threads context` / `douyin context` / `bilibili context`, plus first-reasoning-delta + first-content-delta logs in `streaming.py`.
- **One turn is one `message_id`** (#568): every record the cog and the streamer emit carries it, spans included, because the console exporter this project tees to `./data/logs` prints a span only when it STARTS, with its attributes, and never prints a completion line or a duration — so an unanchored span is not part of the turn and its phase boundary is lost with it. `_message_log_fields`'s docstring owns the contract. What sits between the spans is `gen_reply answer dispatch` (the composition of the request: block counts, `media_parts`, which memory / capability blocks rode, which markers were offered) and `gen_reply pipeline done` (the turn's own total, since no span-end line exists). The anchored layer stops at `cog.py`, `streaming.py` and `input.py`; below it nothing carries a turn id, for two different reasons. `generation.py` and `link_sources/*` do not need one — each call into them is bracketed within milliseconds by an anchored record (`gen_reply image generation start`, `Generating inline image reply`, `gen_reply link context done`), so a turn id threaded through `LinkContextSource.build` and five generator signatures would say nothing new. `attachment/*` and `files_api.py` are the case that genuinely is not solved: one renderer instance serves every turn behind a process-wide `MEDIA_CONCURRENCY` semaphore, so two replies' `gemini upload start` / `done` / drop records interleave with only `filename` and `cache_key` to tell them apart, and the enclosing `gen_reply attachment render` pair is keyed on the RENDERED message (a history message), not the turn. Grepping the turn will not find why an attachment never reached the answer; the render pair for that source message is the way in.
- `reply finalized`'s `url_citations` is `int | None`, and the None is load-bearing: only the Responses bridge reports grounding, only as `url_citation` annotations, so `adapt_interactions_stream` emits `output=None` rather than `[]` and a zero is never written for a backend that reports grounding in another shape. An integer is what the completed response actually carried; reading it as evidence of grounding still needs the positive control under Responses API Gotchas.

### Routes

- **QA** (default): answer streams with the built-in `googleSearch` / `urlContext` tools; carries the inline voice/image/music/video markers and the deep-research marker. It is also the only route carrying the **capability reference** (`gen_reply/capabilities.md`, rendered by `capabilities.py`, gated by `_handle_message_reply(describe_capabilities=...)`), the English feature document that replaced the deleted `/help` cog: `capabilities.py` owns why it is one English document rather than three locales, why it is injected at the FRONT of the answer input, and why its framing line forbids reciting it unprompted. SUMMARY leaves it off (a channel digest is not a question about the bot), and the media persona replies never see it.
- **SUMMARY**: rebuilds at `history_limit=200`, no user or server memory (the author's tone note still rides), no selection. A URL-bearing SUMMARY is rerouted to QA by `_route_classify`.
- **IMAGE** (`_handle_image_reply`): the raw request is first expanded by `PromptGenerator.refine` (`fast_model` + grounding, `IMAGE_PROMPT`, kill-switch `image_refine_prompt_enabled`, best-effort so a director failure falls back to the raw prompt) then renders via `ImageGenerator.render`. Edit needs raw pixels, so it loads bytes via `get_image_source_bytes` (not Files-API handles) and passes them as input images to both the refine (as grounding) and the render. Image sent first; then a best-effort persona reply (`IMAGE_REPLY_PROMPT`, `fast_model`, no tools) via the shared `_stream_media_persona_reply` (history + selected user memory, never server memory), so a reply failure never disturbs the delivered image.
- **VIDEO** (`_handle_video_reply`): native Gemini omni via `VideoGenerator.render` (`interactions.create` DIRECT to Google, the Interactions API being Gemini-only; the route takes the raising `render` since video is always the primary deliverable). `render`'s docstring owns the aspect-ratio rules, `delivery="uri"` with its bounded download-retry, the three input modes and their precedence, the real-mime requirement, and how a soft refusal surfaces as `status != "completed"` with no `output_video`. Two things to know before touching a timeout or a task: `VIDEO_RENDER_TIMEOUT_SECONDS` bounds the omni call ALONE, while the Files-API upload and the URI download each take `FILES_READY_TIMEOUT_SECONDS` on top of it; and for everything but an edit the `task` is omitted so omni infers image_to_video / reference_to_video / text_to_video itself (#317's model-self-decides direction — pin a task back if a deployment finds the inferred mode weak). Clip first; then best-effort `_reply_about_video` → the shared `_stream_media_persona_reply`.
- **YouTube `watch_video`** (`gen_reply/interactions.py`, Gemini-only, kill-switchable): the Responses bridge can't make Gemini watch a YouTube video (LiteLLM's `convert_url_to_base64` fetches the URL as HTML), but the native Interactions API forwards the uri untranslated for server-side fetch — verified against the LiteLLM interactions transform rather than inferred. On a YouTube URL (`utils/youtube.py::YOUTUBE_URL_RE`, found by `_find_youtube_url`) + `RouteClassification.watch_video` (QA-only gate), `_handle_message_reply` swaps that one answer turn to `create_interactions_answer_stream`; `interactions.py`'s docstrings own the input and stream translation that lets the streamer, footer, memory and marker path be reused unchanged. Only a backend swap; no second pass.
    - The current triggering message keeps its complete rendered text for URL matching. Reply-reference spans first strip `USAGE_FOOTER_RE` so a user-controlled memory label in the bot's footer cannot choose the next video, while the wider scan still retains YouTube embed cards.
- **Deep research** (`cogs/research/`, **direct to Google**, kill-switch `deep_research_enabled`): minutes-long cited reports on a Gemini managed agent via the Interactions API. Direct because the proxy 404s the Files API upload and its interactions transform is not a pass-through (it dropped `agent_config`, measured), and Antigravity `background=True` works despite docs — all spike-verified, and none of that evidence survives anywhere else in the tree. ### Inline markers (`markers.py`, `generation.py`)

- The answer model self-selects, inside its own output, which spans to speak (`<generate-voice>...</generate-voice>`, kept visible) and which images / music / video to attach (`<generate-image>`, `<generate-music>`, `<generate-video>`, removed from visible text so the prompt never leaks). Voice spans concatenate into one clip and every image block becomes its own attachment, while music and video are single-per-reply (first non-empty kept). The decision stays inside the answer model so text, clip and media stay coherent; a post-hoc classifier wouldn't. `markers.py` owns the tag set and why the tags are hyphenated — note that extraction runs regardless of the kill-switch, so the element collision it avoids matters even in a disabled deployment. Everything runs after the text is on screen (zero added latency) and rides a single `Message.edit(files=[...])`, since `edit` replaces the attachment list. None adds a function tool on the answer turn, so none has to carry the tool-mixing flag.
- **Voice** rides QA+SUMMARY (`allow_voice`, `COMMON_PROMPT`): the wrapped segments concatenate in order into one `VoiceGenerator` input, with no spoken-length cap by design — the prompt tells the model that multiple spans stitch into one clip, so it tags only the worthwhile lines instead of the whole reply. `VoiceGenerator`'s docstring has the TTS quirks. **Image**, **music** and **video** are QA-only (`allow_image` / `allow_music` / `allow_video`, the last two gated on `music_available` / `video_available`) and each renders best-effort from the marker description, the image and video builders reusing the very `ImageGenerator` / `VideoGenerator` the routes use. `MAX_INLINE_IMAGES` is 9 and `markers.py` has the arithmetic — including that voice + music + video + 9 images can still overflow Discord's 10-attachment cap, where `MediaDeliveryPlanner.plan`'s clamp is the backstop. Uploaded images ride into `<generate-image>` as edit sources and into `<generate-video>` as reference pairs, loaded once by the shared `source_images_task`. Unlike the IMAGE route, a marker description is NOT run through `PromptGenerator` (the answer model already authored it with grounding), so `image_refine_prompt_enabled` does not affect it. The markers are deliberately separate from the IMAGE/VIDEO routes (image-first UX) and routing decides which runs first, so they never double-fire; the IMAGE/VIDEO routes never speak or inline-image. Unlike the voice clip, the bot's own music attachment is NOT skipped from later history input (`input.py` skips only `reply.wav`): the `<generate-music>` description is stripped from the visible reply, so the clip is the only trace of the song and is deliberately re-ingested so a later turn can reference it.

### Responses API Gotchas

- Strict role/content part pairing: `user` / `system` / `developer` use `input_*` parts; `assistant` uses `output_text` or `refusal`. So a message with attachments falls back to `role=user` (see `_assemble_input_message`). Prefer string-content shorthand when there are no attachments.
- The top-level `instructions` parameter has `developer` authority and outranks everything in `input`, but does not persist across turns. Put behavior rules there (or in `COMMON_PROMPT`), never in an input-side wrapper.
- Separator messages use `role=system`, not `developer`, for Gemini and Claude compatibility through LiteLLM.
- Grounding is reported differently per surface, so a check that knows only one shape reads a grounded reply as ungrounded: the Responses bridge emits ONLY `annotations` of `type: url_citation` (urls are `vertexaisearch.../grounding-api-redirect/`) and carries no `groundingMetadata` anywhere, while chat completions and the native API do carry `groundingMetadata` / `webSearchQueries`. Run a builtin-tools-only positive control before reading any zero as an absence; three separate investigations called a grounded reply ungrounded for want of one.
- Mixing a custom function tool with the built-in `googleSearch` / `urlContext` in one Gemini request DOES work; what it takes differs per surface, and both surfaces were measured live in 2026-07 (proxy path against the running LiteLLM 1.93.0, native path both direct to Google and through the `/gemini` pass-through, which proved byte-transparent). Through the LiteLLM proxy it needs `include_server_side_tool_invocations: true` flat in `extra_body`. Without that flag LiteLLM strips the search tools client-side before dispatch (`_resolve_search_tool_conflict`) and the reply degrades to zero annotations with no 400; the silence is LiteLLM's, not Google's, whose own answer to the unflagged mix is a hard 400 naming the flag. With it LiteLLM emits `toolConfig.includeServerSideToolInvocations` (`vertex_ai/gemini/transformation.py:1167`) and grounding survives at full strength, equally on Responses, Responses-streaming and chat completions, and on `gemini-3.1-pro-preview` as on flash. On `interactions.create` that flag is unsettable (`Unknown parameter 'tool_config'`) and unnecessary: every concrete model tried combined natively (`gemini-3.1-pro-preview`, `gemini-3.1-flash-lite`, `gemini-3.5-flash`, `gemini-3.6-flash`) while BOTH `*-latest` aliases were rejected. Only the behavior was measured, not the cause, but it rhymes with the alias-does-not-carry-the-substring trap `RuntimeModelCatalog` documents for effort, so treat a bare alias as suspect wherever a capability gate might read the model string. Do not re-derive any of this from LiteLLM's source alone, and do not trust a single sample: the drop warning (`vertex_and_google_ai_studio_gemini.py:569`) is deduplicated, so its presence in the proxy log is not a per-request signal, and the proxy runs `cache: true` with a key that ignores `extra_body`, so a flagged request silently replays an unflagged cached answer unless the prompt carries a nonce AND `extra_body` carries `{"cache": {"no-cache": true}}`. Both traps produced confidently wrong readings before they were caught. What has NOT been lifted, re-measured 2026-07 at N=20 per condition on `slow_model`: one turn never carries both, rather than carrying both unreliably. A function call ends the turn with empty text (145/145), so no grounded *answer* can ride a lookup; whether a server-side search silently ran on that turn is unmeasurable, since there is no message item to hang annotations off. The second turn with the tool result fed back does ground (19/20), and streaming behaves identically to non-streaming. Three traps before adding any function tool to a turn that also searches, all measured: no runtime call sends `extra_body` at all today (see the mock-testing gotcha below), so the answer turn is safe only because no function tool rides it and attaching one without reintroducing the flag silently ends grounding on every QA reply; merely *offering* the tool made the model call it on a pure-search question 20/20 and zero the grounding, and the restraint wording already in `MEMORY_SELECT_PROMPT` does NOT fix that (10/14 still spurious) while a sentence explicitly exempting live-external-fact questions does (0/14); and naming a tool in `instructions` without attaching it makes the model hallucinate that call (3/12), which ends the turn just as a real one would.
- **No runtime call sends `extra_body`, and a mock-testing key in one is a hard 400.** Since LiteLLM 1.96 the proxy gates every client-supplied mock param (`proxy/route_llm_request.py::raise_if_mock_testing_params_disallowed`, covering `mock_testing_fallbacks`, `mock_testing_context_fallbacks`, `mock_testing_content_policy_fallbacks`, `mock_testing_rate_limit_error`, `mock_timeout` and `mock_delay`) and the test is `name in data` — the VALUE is never read. So the `{"mock_testing_fallbacks": False}` every call carried, itself a no-op since LiteLLM only mocks on a truthy value, 400'd the whole reply pipeline the day the proxy was upgraded (#496). Deleted rather than unblocked with `general_settings.dangerously_allow_mock_testing_request_params: true`, which is exactly as dangerous as its name says: it would let anything holding a key inject synthetic failures into production traffic, and nothing here ever asked for a mock. A future `extra_body` is fine (the grounding flag above, the `{"cache": {"no-cache": true}}` the dev scripts pass); a mock-testing key in one is not, whatever its value.
- The code-execution built-in tool is intentionally omitted from `ModelSettings.tools`; its docstring has the narrow-MIME-allowlist reason it cannot coexist with the Files-API attachment path, and why the search/url tools have no such limit.
- Gemini prepends leading newlines to the first reasoning and content delta; `_on_reasoning_delta` / `_on_content_delta` strip them. Thought summaries do not come back through chat completions: on the Responses bridge they arrive as `reasoning_summary_text` deltas, and on the native Interactions API as `thought_summary` step deltas, which `gen_reply/interactions.py` translates into that same Responses event so one streamer serves both.
- `client.images.edit(image=...)` needs raw `bytes`, not image-reference dicts.
- **Media reaches the model by upload, never by URL.** Upload it to the Gemini Files API (`gen_reply/files_api.py`) and reference the full `https://.../files/<id>` uri as an `input_file` `file_id`. `tests/test_model_media_parts.py` enforces it by AST and its module docstring carries the reasoning; the two anchors that live only here are LiteLLM's rewrite site (`convert_url_to_base64`, `llms/gemini/chat/transformation.py`, which also swallows a failed fetch) and the dedicated no-fetch pass-through a Files uri hits instead (`llms/vertex_ai/gemini/transformation.py:560`). Bytes already in hand may be inlined as a `data:` URI (that fetches nothing). The Threads link builder was the last exception and was migrated in #341.
- Per-token pricing comes from `utils.model_pricing` and its cached LiteLLM JSON; do not hardcode rates. Its module docstring owns the whole never-raises chain (#452) — the mirror, the table held for the life of the process, and what an empty one costs downstream (`$0.00000000` in the footer and a `{"text", "image"}` modality baseline that keeps text, images and documents but drops audio and video) — plus the upstream-only recovery that `cli.py`'s `price_table_task` drives (#473). Two things it leaves out: the per-entry-drop reasoning sits on `_decode_table` rather than up there, and the narrow scope of that recovery is deliberate — rate drift is a different question from recovery, and a periodic re-fetch on a process with nothing wrong with it is what #473 did not ask for.

## Economy

- DB files under `data/database/`: `messages.db` (log_msg), `economy.db` (per-user 虛擬歡樂豆, jackpot pools, casino ledger), `games.db` (Blackjack history, cleanup targets), `feedback.db` (user reports, see Other Cogs). Two separate engines sit on that one `games.db` — `cogs/games/` and `utils/message_cleanup.py`, the latter a util module rather than a cog — and that is intentional.
- `services/economy/database.py` owns the module-level `_engine` (its docstring has the pool-leak + test-monkeypatch reason); do not move it to `cached_property`.
- `UserAccount` has no `guild_id` (identity, VIP, flags are cross-server). Money columns are `StoredInteger` decimal text parsed to Python `int` (`utils/stored_integer.py` has why): balance in `user_wallet`, loans in `loan_proposal` / `loan_contract`, daily casino counters in `casino_account`.
- Invariant: every applied positive delta bumps `total_earned`, every negative bumps `total_spent`, so `total_earned - total_spent == balance`. There is no transaction table.
- Money inputs are string `SlashOption`s parsed via `utils.amount_parsing.parse_decimal_amount` and wrapped per domain; malformed text returns `build_invalid_amount_embed` ephemerally before any mutation. Reuse it for any numeric input that can exceed Discord's int cap.

- `credit_with_repayment` is the single income facade (message reward, casino payout). Its name is a leftover: nothing auto-repays a loan any more, so income lands fully in balance and `total_earned`, and a long-term loan is settled only by an explicit repayment or collection command.
- Loans: personal loans debit the lender on acceptance; central-bank loans mint on approval and burn on repayment / collection (no lender credit). Proposals expire after `LOAN_PROPOSAL_TIMEOUT_SECONDS`. Acceptance prepays `MIN_INTEREST_DAYS` of interest, so do not zero `interest_due` at contract creation.
- `is_central_banker` (set offline by direct DB write) is separate from Discord admin; keep `ECONOMY_ALLOW_CENTRAL_BANK_SELF_APPROVAL` unset or `false` in production.
- Admin tweaks go through `adjust_balance(..., allow_negative=...)`, never casino settlement helpers (it skips loans and daily casino counters).
- `/leaderboard` sorts `StoredInteger` text DB-side with `LIMIT` before rows reach Python (`top_n`); `hide_from_leaderboard` accounts are omitted; write paths must call `invalidate_economy_leaderboard_cache()`, which clears the two row caches and nothing else. The rendered PNGs (`cogs/economy/boards.py`) are a separate cache keyed on the rows they drew, and no write path may reach into it — which is what keeps Pillow out of the ledger's import graph (#415). `/loss_leaderboard` reads gross `daily_loss` from `casino_account` (player-side Blackjack and Dragon Gate deltas only, so wins don't offset it). The bot is just another player here.
- Casino-system P&L lives in the `casino_ledger` row in `economy.db`; `/casino` reads the ledger, `/pocat` reads the bot's wallet. Do not reuse the bot's `user_wallet` as the house ledger. ## Memory

- **The path is the privacy boundary** (#408, replacing the per-bullet `[src:...]` tag it removed). File-backed per-user markdown under `data/memories/<user_id>/`, keyed by user id (cross-server, shared with DMs). The consolidated tier is ONE FILE PER FACT filed under the compartment allowed to read it — `global/`, `g/<guild_id>/`, `dm/` — so reading for guild G is two path joins, with no tag parser, no read-time content filter and no fail-closed rule. Beside it sit the per-scope tiers: `detail.md` (append-only cold evidence), `raw.md` (phase-1 staging, deliberately still ONE file) and `tone.md`. `main.md`, `main.bak.md`, the `v1` header and the identity line are gone. Layout rationale in `store.py`'s docstring, the file format and the section vocabulary in `facts.py`, the write/age half in `deltas.py`. Do not move it into SQLite and do not add legacy-layout fallbacks.
- **Fact file** (`facts.py`): a `---` fenced header of single-line `key: value` pairs, then the body; its docstring has the shape and why it is deliberately not YAML. The model authors `summary` / `section` / `durability` / the body and names `subject_id` / `from_keys`; code owns the rest and mints `id` itself from `sha256(compartment + summary)`, so the id is deterministic, per-compartment unique and **never influenced by conversation content**, which is what makes path traversal structurally impossible. Provenance is not hidden from the model, though: an update or delete has to name the id it edits, so `render_existing_facts` hands the id, `keys` and `subject_id` back (`typings/memory.py::MemoryFact`). `keys` is the retry-idempotency handle — a `create` whose keys overlap an existing fact becomes an `update` of it. A stored `compartment` disagreeing with the directory holding it is skipped on the READ path only; the next rebuild removes it, since a rebuild replaces the directory rather than the readable part of it.
- **Sections** are ASCII keys rendered to Chinese headings per flavor (`section_headings`), so the structured schema stays English while the injected document stays Traditional Chinese. That the RENDERED shape stayed byte-compatible is load-bearing, not cosmetic: `allowlist_ids_from_server_memory` parses `## 成員稱呼` back out of the rendered server document, and the reply prompts tell the model to read that table. A `member_alias` fact carries `subject_id` (the member, distinct from `owner_id` = the scope) and the renderer appends its `[id: N]`, so the id can never be hallucinated onto the wrong row; its BODY is code-owned as well (#464, `render_member_alias_text`), with the model's own `text` unread for that section. Stored prose rows from before it are not migrated — neither offline script targets a server scope narrowly — and self-heal when the member is next observed, since `vocab.member_alias.<id>` resolves the delta onto the same fact.
- **Consolidation emits deltas, not a whole file** (`extraction.py` has the delta schema, `pipeline.py::_consolidate_locked` the fan-out and the ONE timeout wrapping it, which is what keeps the worst-case lock hold from multiplying by the compartment count — the per-compartment bound inside it went with #529, since the client already bounds a single call). `partition_raw_entries` buckets one raw batch over the scope's compartments in CODE off the `- sharing:` / `- source:` fields; only the compartments it routed evidence to run, `global` first so every later one can take its facts as a read-only `<global_reference>` and neither restate nor silently contradict them. **Each call sees only the evidence routed to the compartment it writes** — that, not a prompt rule, is what makes "a guild-locked observation cannot reach `global/`" structural. Information flows global -> guild, never guild -> global. The raw batch retires only when EVERY compartment applied; a retry is safe because deltas are id-keyed upserts.
- **Rejection is for shape errors only**: the LLM call failing, or the net-delete cap (exempt on the regeneration path, because replacing the whole set is what that path is for). Everything else sanitizes per delta, and `deltas.py`'s module docstring has the asymmetry's reasoning in full — why a whole-batch rejection is not a retry but a permanent freeze. Read the sanitizer before assuming what a malformed delta costs: an unknown section or an empty body drops that one delta, but an id naming a fact that is gone becomes a `create` instead, and an unusable `subject_id` is dropped to None rather than costing the delta, `member_alias` being the one section that drops the whole row instead because there the id IS the row. That split is #527: the digit test used to guard `member_alias` alone while the cast beside it was unguarded, so on a user scope — which has no `member_alias` section at all — a model-authored non-numeric id raised out of `apply_deltas` and abandoned every compartment the fan-out had not reached yet. `_rewrite_shrank_too_much` and the `v1`-header gate are gone.
- **Aging is code, not prompt prose**, now that `last_confirmed` is stamped: `sweep_stale_facts` (`deltas.py`) carries the two expiry rules, the per-compartment anchoring behind the second, and why `permanent` durability, the `permanent` SECTION and `member_alias` never age. The sweep runs over EVERY compartment after a successful fan-out, not just the ones this batch touched, or a guild the user stopped visiting would hand back its months-old `recent` facts. The `[~YYYY-MM]` / `[YYYY-MM-DD]` markers the model used to write are gone.
- **Size governor**: `read_memory_document` renders sections in order, newest first within a section, and stops at `MEMORY_INJECTION_MAX_CHARS` with an explicit truncation notice. It never deletes, which is what stops it fighting the next consolidation over facts it would immediately write back. Calibrated against the live store — median ~800 B, p90 4.8 KB, max 25 KB — so it is a backstop that fires on nobody.
- **Read caching is not optional.** `resolve_user_memories` is synchronous and can carry 8 users per reply; one fact per file would otherwise be hundreds of opens on the event loop. `read_memory_document` is cached on `(scope, compartments, flavor, max_chars)` against a per-scope write generation that every `write_fact` / `delete_fact` / `prune_compartment` / `delete_memory_files` bumps, so a repeat read costs zero syscalls. The counter is exact because every write goes through the store under `scope_lock`; editing the tree out of process while the bot runs is not supported.
- **Two-phase write** (`services/memory/`, fire-and-forget; must never add reply-path latency; LLM failures silently keep the previous state): phase-1 `MemoryExtractorAI.extract` after each QA reply (per-user in-flight de-dupe replays only the newest skipped turn) + a phase-1.5 evaluator, then deterministic gates (`_validated_draft` / `_is_accepted_observation`) reject casual mentions, hypotheticals, bot suggestions, other-user context, weak confidence, non-target observations, and duplicate `normalized_key`s before raw append. The `durability` ladder is `volatile|session|recent|stable|permanent`. Phase-2 runs once `RAW_CONSOLIDATION_THRESHOLD` accumulates and the cooldown elapses (`RAW_CONSOLIDATION_MAX_BYTES` bypasses cooldown), capped by `MEMORY_GLOBAL_CONCURRENCY`. Thresholds + reasons in `constants.py`. Models: `memory_extractor_model` for phase 1, `memory_writer_model` for both later gates, split on the one seam worth tuning at.
- **The sharing gate is tighten-only, and code owns every rule but one.** `_sanitize_observation` forces `source_only` on `recent_context`, on `evidence_kind="ongoing_situation"`, on an `[id: N]` / `<@N>` token naming anyone but the target, and on any observation whose text literally names another conversation participant; `extraction.py` has where that roster comes from and why the two matching thresholds are asymmetric. The remaining rule is the phase-1.5 evaluator's: naming or describing anyone but the target is `source_only` even with no id token. **Do not add a Chinese pronoun/relation lexicon** — it was measured against the live store and re-locks 14.5% of all `global` observations (`他` is a substring of `其他` and `吉他`).
- **Anti-injection** (plumbing in `extraction.py`, not `prompts.py`): the transcript renders column-0 `[message <n> | <role>]` markers with indented bodies so user text can't forge a boundary; `sanitize_identity` (`utils/llm_transcript.py`) neutralizes `[id:`-lookalikes in names; `redact_secrets` (`_SECRET_PATTERNS`, shape-specific, deliberately no bare-hex rule so git SHAs survive) runs on the transcript and every model output. Prompts treat conversation content as data, never instructions.
- **Read path is deterministic first, optional selector second.** Code always resolves the current author, resolved reply-chain authors and current-message explicit mentions in that order; `build_memory_allowlist` sanitizes and dedupes those trusted Discord users, then `resolve_user_memories` enforces both the per-user allowlist and the compartment boundary. `memory_tool.py` owns `compartments_for_reading`'s four cases and why a `MemoryCandidate` carries two labels rather than one (#463). Only a public guild channel with additional ids in the rendered `## 成員稱呼` table starts `_select_user_memories`; its `MEMORY_SELECT_PROMPT` asks solely whether the latest message obliquely refers to one, timeout or error loses only that optional memory, and the selector never displaces deterministic participants. What the ROUTES do with all this is stated nowhere else: SUMMARY runs neither deterministic user-memory reads nor selection, IMAGE/VIDEO consume the speculative context, and extraction is handed a memory-free, target-centered `message_list` (`target_centered_memory_messages`) so it never re-ingests stored memory.
- **Restart-resumable phase-1 inbox** (`services/memory/database.py`, tables `memory_job` / `memory_token_clock` in `reply.db`): the markdown store stays the source of truth — do NOT move memory *content* into SQLite; this DB only persists the *progress* of the fire-and-forget pipeline so a redeploy mid-extraction is not lost. Its module docstring owns the per-scope state machine and the logical-token clock that keeps an NTP correction from making a clear older than the transcript it erases; `clear_scope_memory`'s own `Raises` section owns why the tombstone write is the one memory DB call that is not best-effort, while everything else goes through `_safe`. `ReplyGeneratorCogs.on_ready` (guarded by `_resume_started`, fires every reconnect) starts the git worker, re-enqueues only `pending` / `failed` rows and sweeps every over-threshold scope; the scope lock plus the under-lock `_should_consolidate` re-check keep a resumed extraction and the sweep idempotent. Consolidation itself needs no job rows since `raw.md` is its durable, re-entrant queue.
- **Tone note (`tone.md`)**: persona-independent delivery preferences (the qualities the user wants, never a named persona, so a `PERSONA_CHOICES` change never strands it) live in their own per-user tier, OUTSIDE the compartment tree — cross-server safe by construction, the deliberate exception to the boundary. It is therefore the one thing that must NOT be partitioned: ~48% of observations are `source_only`, so a note fed only the global bucket would stop updating for half of all conversations. That is why `_update_tone_note` is its **own** LLM call rather than a field on the `global` compartment's, handed the whole batch's tone-bearing observations with no `<existing_facts>` and no `<raw_entries>`, and why its `deltas` are discarded by code — the unpartitioned input it needs can never become a stored fact. Each of those observations is tagged with its `evidence_kind`, which is load-bearing rather than decorative: the note merges batch after batch, so an untagged bullet list converges on whichever reading has the most bullets, and `tone_evidence_from_raw`'s docstring carries the live-store case where one stated preference lost to five inferred from the user's own trash-talk and the note came out reversed. Folding it into the global call would have demoted the whole boundary back to a prompt rule. Injected for the message author on EVERY reply with no selection (`ReplyContext.tone_block`, one file read, even on SUMMARY; media persona replies too); `PERSONA_CHOICES` says the note overrides the default voice, delivery only.
- `regenerate_main_memory` (`pipeline.py`) is the shared pure-evidence rebuild for `/memory regenerate` (own `MEMORY_REGENERATION_COOLDOWN_SECONDS`) and `scripts/regen_memories.py`: it rebuilds every compartment from the detail tail + unconsumed raw only, never the existing facts, and deletes what it did not re-emit. `store.py::prune_compartment` and `pipeline.py::_prune_rebuilt_compartment` own the #469 / #474 / #475 reasoning — why deletion is decided by the DIRECTORY listing rather than by the facts that could be read back out of it, why a file the store never wrote is left alone and named in the log instead, why a compartment holding neither evidence nor a readable fact is pruned with no LLM call at all, and why the count of unreadable files removed rides out on a `RegenerationReport`. It is the ONE path allowed to lose most of a compartment at once (`allow_mass_delete=True`), which is also why the #408 compartment migration needed no migration-only writer. `scripts/regen_memories.py` is the ONE offline entry point (#465 folded `scripts/migrate_memories.py` into it once the store had no `main.md` / `main.bak.md` left for its deletion step to find); its own docstrings carry the stop-the-bot warning, the typed-`y` confirmation behind rebuilding by default (#484) and the report's shape. The part neither side states: `/memory regenerate` is the live-safe single-scope path precisely because it runs inside the bot under `scope_lock`, while the script is a second process whose closing `clear_raw` unlinks whatever `raw.md` gained while it worked — do not restate the two as equivalent, which #465's own framing did.
- **git history** (`git_history.py`, `MEMORY_GIT_ENABLED`): `data/memories` is a local repository, never pushed; a successful consolidation, rebuild or clear enqueues a commit of that ONE scope directory. Its module docstring owns the three properties that make committing from inside a running bot safe, and the deliberate #408 decision that a `/memory clear` commits the deletion without erasing the history behind it; its comments own the two container facts that each alone would make the feature a permanent production no-op. The reason living nowhere else: the `git status --porcelain` guard before `add` is required rather than an optimization, because `add` on a never-tracked, now-absent path exits 128.
- All writes serialize under `scope_lock(scope)`; fact writes are atomic tmp + `os.replace`; in-flight updates check `cleared_since` so a clear isn't resurrected. Tests use the `memory_isolated_dir` fixture, which also resets the render cache + generation counter and disables the git service so no test can ever commit against the live store.
- `store.py` / `pipeline.py` are keyed by an opaque `scope: str` (the subdir under `data/memories/` and the registry key); `user_scope(user_id)` / `server_scope(server_id)` build it, and one store + one pipeline serve both flavors (shared `MEMORY_GLOBAL_CONCURRENCY`, per-scope de-dupe + cooldowns). **`scope` is the owner key and `compartment` is the visibility axis; they are never the same word.** `MemoryExtractorAI` carries its phase prompts as fields; `extract(subject, ...)` takes a per-call `target_user_id:` / `target_server_id:` subject.
- **Per-server (community) memory** at `data/memories/bot_memories/<server_id>/global/` (`BOT_MEMORY_DIR_NAME`, fixed and non-numeric so it is not confusable with a user scope on disk and survives a bot-account change) via the same store, the same delta protocol and the same reader, with `server_prompts.py`'s own section vocabulary (rendered by `facts.py` to 伺服器輪廓 / 社群文化 / 常見話題 / 重要事實 / 成員稱呼 / 近期脈絡). It has exactly ONE compartment because its observations carry no source or sharing to route by and a server memory is per-guild by construction — same code path, one hardcoded bucket, no second writer. `gen_reply` reads it once (`_read_server_memory`) and injects `render_server_memory_block` into both the selection request and the answer (zero extra latency), and schedules a server-scope update after each guild QA or SUMMARY. `## 成員稱呼` is the sole carve-out from the no-individuals rule, recorded with `durability=permanent` so the sweep never ages it. DMs skip both; SUMMARY skips user memory but still records server memory. The write side is gated by `_source_channel_is_public` so content a channel's `@everyone` can't view never feeds the member-readable server memory.
- User-facing commands read, rebuild, or erase the PERSONAL scope only: `/memory show`, `/memory regenerate`, `/memory clear`, plus the read-only `/memory server show` (community memory stays operator-maintained, so there is no server-side clear). `/memory show` renders one section per compartment, labelled with who can see it (`compartment_label`) — the information is structural now rather than an inferred tag, so showing the owner where each fact can resurface costs nothing. `/memory clear` opens a `MemoryClearConfirmView` and the button — never the command — calls the single orchestration point `pipeline.py::clear_scope_memory`, whose docstring owns the protocol: **a clear is only whole if all four holdings are neutralized** (the files are removed, the deferred replay is dropped, in-flight work sees the process stamp, and reply.db keeps only a transcript-free tombstone), why `clear_job` is the ONE memory DB call not wrapped in best-effort `_safe`, why it RAISES against an already-newer token rather than no-opping (returning False there let the caller unlink the files with the pre-clear transcript still resumable, which is #397 / #400 / #401's failure through a different door), why the clear deliberately does not take `scope_lock`, and why a cancelled clear still records what it erased (#428 — whose own text, and an older `views.py` comment, both claimed cancellation shows Discord's "This interaction failed"; measured against nextcord, it leaves the prompt silently unedited instead, which is why the audit line carries `caller_cancelled`). Seven named regressions are pinned in `tests/test_memory.py`; a test reading a DEFERRED turn's row must first drain `pipeline._db_tasks` through `_wait_for_persisted_writes`. An offline wipe while the bot is stopped must also create a tombstone or remove that scope's row; an online clear must use this protocol because staging writers can still exist.

## Other Cogs

- `parse_threads/cog.py` expands a Threads link into embeds and uses reactions for status; no extra reward. Its module docstring owns the mention rule and why replying to the expansion is not a trigger; `_build_embed_plan` owns the 10-embed allocation, the two reserved slots and both length guards; `utils/threads.py` owns the share-link handling and the rule that a published URL must never name whoever shared the post. Three things the code cannot say for itself: the old `total_size` byte guard is gone (oversize videos are hosted as URLs via `MediaDeliveryPlanner.plan`, and the whole post is refused only when they cannot be hosted, via `plan.dropped_items`); there is deliberately no media-count guard, so an oversized carousel degrades to its first images rather than refusing the post; and this cog walks the whole chain (`MAX_THREADS_POSTS` is gen_reply's cap, not its own), which is why the omitted-post page ceiling has to exist here — that notice is strictly additive and must never cost what it reports on (#426). `parse` is a context manager over the SAME walk as `parse_metadata`, downloading the target's video being the only difference left between them; it shows `.chain` plus the target's `.quoted` and no comments, since the 10-embed cap has no room for them, while `gen_reply` runs `parse_metadata` and fetches the target's media and the quoted post's.
- `parse_douyin/cog.py` mirrors `parse_threads` for Douyin URLs; its module docstring carries the auto-expansion justification and the request-volume constraint behind `utils/douyin.py`'s per-URL lock, semaphore and caches, and `douyin_failure_message` is the single failure mapping (`video/cog.py` uses it too). `DouyinConfig.auto_expand_enabled` stops the UNPROMPTED traffic during a WAF incident and only that — `/download_video` and the reply pipeline's ingest carry their own switches. `_download_to`'s `max_bytes` is a fail-fast guard rather than a policy, and who passes what is the part its docstring cannot say: `/download_video` and this cog pass `None` (an oversize file is the media host's job), while the AI path passes only the Files API's 2 GB ceiling.
- `video/cog.py` keeps progress text on the deferred original message, then edits that same message with the final file. The native path appends the source URL; the hosted path omits it, since a second URL stops Discord rendering the inline player.
- Scratch media downloads go to the system temp dir; `VideoDownloader` / `ThreadsDownloader` (`utils/downloader.py`, `utils/threads.py`) require `output_folder` (no default) and never put scratch downloads under `data/`. Files are deleted after delivery — and a path that can ABANDON a download needs a per-invocation directory rather than `tempfile.gettempdir()`, because `asyncio.to_thread` cannot be cancelled, so the worker keeps writing past the give-up and only a directory that goes away takes those bytes with it. `utils/scratch_dir.py::scratch_directory` is that directory at all four sites (`/download_video`'s two branches, `parse_douyin`, `parse_threads`), never `tempfile.TemporaryDirectory`, and its module docstring owns the whole argument: what the directory is FOR differs per path, and its teardown can lose a race with the worker it is stopping, which `TemporaryDirectory` hands to the `with` block's owner — who has already told the user what happened. The rule the WRITERS owe it lives on `utils/threads.py::download_media` instead: whoever writes into that directory must never re-create it, so `ThreadsDownloader.parse` and `DouyinDownloader.download` mkdir once up front and their per-file writers do not, because a mkdir between two files rebuilds the directory the give-up just used as a stop signal. `VideoDownloader` is the one that cannot keep it (yt-dlp re-makes the output dir per DASH format), which is why the yt-dlp path stops its worker with `download_with_stop_signal`'s event plus a bounded join and reaches the removal as a live writer only in the case that function logs.
- `auto_unmute/cog.py` clears the bot's own timeout, finds the moderator from the recent audit-log window, and replies in the last active human channel or the guild system channel (its docstrings have the flow).
- `cogs/template/` is a real loaded cog despite the name (it holds a `cog.py`, so the loader takes it): it owns `/ping` plus the simple message-trigger reactions and is listed in `gen_reply/capabilities.md`. It is not a scaffold to copy or delete.
- `log_msg/cog.py` logs human messages and this bot's own replies, never third-party bots; streaming replies converge via UPSERT on `discord_message_id`. It owns the module-level `_sql_engine`; do not move it to a `cached_property` (per-message would leak the pool / dialect / inspector cache, see the comment).
- `feedback/cog.py` + `cogs/feedback/`: `/feedback` opens an ephemeral panel of the caller's own reports and files new ones as issues on `FEEDBACK_GITHUB_REPOSITORY` over `httpx` (no `gh` CLI in the image and no MCP server at runtime). The module docstring owns the ordering that makes a report unloseable, why a missing token is an operational state rather than a switch, and the deliberate absence of an admin surface; `TicketRow.status` owns the derived-per-panel-open rule and what it knowingly gets wrong in the list view; `github.py` owns the maintainer / reporter comment rules, and `auth.py` the swappable credential. ## Conventions

- Environment-backed config classes use `pydantic_settings.BaseSettings` with explicit `validation_alias=AliasChoices("ENV_NAME")`; `.env` is loaded at import time.
- Pure shared result types, enums, and constants live under `typings/` when they don't depend on cogs or utils.
- **Every wall-clock bound whose expiry produces a failure or a degradation lives in `typings/timeouts.py`** (#529), and `tests/test_timeouts.py` fails on a numeric literal written as one anywhere else — including `asyncio.timeout(delay=30)`, a local `x_timeout_seconds = 15.0` and a `"socket_timeout"` params key, since those are the shapes that made three download paths invisible. The module's docstring owns the scope rule and what is deliberately outside it; the test's allowlist is that exclusion made mechanical. Two things neither says. A bound that wraps ONE LLM call purely as a liveness backstop belongs in neither place: `openai` bounds its own requests (measured, and looser than it looks — `max_retries=2` on a 600s read), so the test for keeping one is whether anything is WAITING, which is why `google-genai` wrappers (`timeout=None` by default) and the product deadlines all survived while the memory and write-up backstops went. And `utils/llm.py`'s `timeout_seconds` is optional for exactly that reason — passing one is a claim that this caller has a deadline of its own.
- Use `pydantic.BaseModel` for structured data and type-managed payloads, including service/helper classes. No `dataclass`; no loose `object` / `Any`. Every field carries `Field(description=...)`, plus `examples=` where a value is worth illustrating; a required field uses an explicit ellipsis: `Field(..., description=...)`.
- Log severity follows the ladder in `.github/CONTRIBUTING.md#logging`, keyed on how tolerable the failure is rather than on how deep it happened; that section also owns the exception-attachment and broad-`except` rules. `LOG_LEVEL` (default `debug`) sets the console + `data/logs` floor.
- Ruff is formatter and linter; `ty` is the only type checker (both configured in `pyproject.toml`, which records why mypy was removed in #356). Use narrow `# noqa: <rule>` comments with a reason.
- `ty` types a pydantic field annotated with an arbitrary class (anything pydantic cannot model itself: `nextcord.Message`, `genai.Client`, `AsyncOpenAI`) as `Any` in the `__init__` it synthesizes, so those constructor arguments are unchecked at every call site; annotations pydantic does model keep a real type (`int` becomes `LaxInt`). The `SkipValidation[T]` wrapper is irrelevant to this — the signature is identical without it, and dropping it only changes runtime validation. Since #356 there is no second checker, so a wrong handle handed to one of `gen_reply/`'s services surfaces at runtime.
- Keyword arguments are required for normal calls, including single-argument ones; do not add bare `*`. Allowed positional idioms: `len(x)`, `str(x)`, `Path("x")`, exception constructors, variadic collectors, `logfire.info("message")`.
- Avoid intermediate one-level aliases such as `usage = responses.usage`.
- Import functions by name and call them unqualified (`from pkg.mod import do_thing`); a module-namespace import is a last resort with a reason.
- An `asyncio.Lock` / `Semaphore` / loop-bound registry must not outlive one event loop, module-level or on a process-wide singleton: each test runs on a fresh loop and the primitive raises `is bound to a different event loop` there (`utils/asyncio_locks.py`'s docstring has the binding mechanism, and why building it lazily does not help). Use its `LoopLocalLock` / `LoopLocalSemaphore` / `LoopLocalRegistry` / `KeyedLockManager`, which rebuild on a loop change.
- LLM latency matters; do not add extra LLM calls for cosmetic improvements.
- `docs/` is generated by `make gen-docs`; do not hand-edit it. Do not touch the README badge block unless explicitly asked.
