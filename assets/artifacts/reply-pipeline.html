走 LiteLLM Proxy

直連供應商

00

兩條網路路徑，以及為什麼一定要有第二條

整個專案原則上只用一套 SDK：OpenAI SDK 打 LiteLLM Proxy，模型字串換一下就能換後端。直連供應商是例外清單，不是預設。

主要路徑 OpenAI SDK → LiteLLM Proxy 分類、答案串流、圖片生成、TTS、提示詞導演、記憶寫入、研究討論串標題。全部都是 Responses API（或 images / audio.speech 端點）。每個請求都帶 x-litellm-end-user-id，所以成本可以歸到人頭上。
例外清單 google-genai / anthropic SDK → 直連 Google：Gemini Files API 上傳、影片生成與編輯、音樂生成、看 YouTube 的那一輪回答、深度研究 agent（GEMINI_API_KEY）。Anthropic：Claude 答案模型的圖片與 PDF Files API 上傳（ANTHROPIC_API_KEY）。

四個非直連不可的理由

  1. Interactions API 是 Gemini 專屬的。 Proxy 沒有等價的轉換，影片與音樂生成只有這條路。
  2. Proxy 會把 YouTube 連結當成一般網址抓下來。 抓回來的是 HTML，模型永遠看不到影片本身；原生 API 則是把 uri 原封不動轉給 Google 自己去抓。
  3. Files API 上傳必須能 poll 到 ACTIVE。 Proxy 的檔案資源回報的是已棄用的狀態，引用一個還沒 ACTIVE 的檔案會間歇性讓整個回答請求 400。
  4. 深度研究的 agent 設定會被 proxy 的轉換丟掉。 實測過，不是推測。
一把金鑰的規則

Files API 上傳的檔案只有上傳它的專案或工作區讀得到，而且一個請求同時引用兩把金鑰的檔案會直接失敗。所以「上傳附件的金鑰」必須等於「回答這則訊息的金鑰」。實務上就是 bot 端用 GEMINI_API_KEY 直接上傳給 Gemini、用 ANTHROPIC_API_KEY 直接上傳給同一個 Anthropic 工作區的 Claude，而 proxy 裡的對應對話類別名也綁同一把。第二把、第三把 Gemini 金鑰只服務不會攜帶檔案的工作（媒體生成、TTS、音樂、embedding）。

01

什麼時候 bot 才會理你

兩個入口通往同一條流水線。差別只在「回覆要送去哪裡」、「讀得到什麼歷史」、「能不能對來源訊息按表情」。

入口 A · Gateway 訊息事件

  • 發話的是 bot？
    • 是 → 完全忽略
  • 這是私訊嗎？
    • 是 → 一律回應，不需要提及
    • 否 → 訊息內文必須出現 <@bot>。只看內文不看 mentions 欄位，因為回覆通知會把 bot 塞進 mentions，那會讓「回覆 bot 貼的 Threads 展開」也被誤判成在叫它
  • 這個頻道正在被深度研究佔用嗎？
    • 是 → 跳過，研究討論串在報告落地前是它自己的工作區；報告一落地就解除
  • 去掉提及後還有字，或有附件、貼圖、轉發嗎？
    • 都沒有 → 加一個 ❓ 然後回一個 ?
轉發訊息

Discord 的轉發會把 content、embeds、attachments 全部清空，真正的內容躺在快照裡。所以轉發不會被當成空訊息擋掉，而且快照裡的文字會併進使用者提示詞（接在轉發者自己的留言後面）——這樣「@bot 幫我」轉發一張「畫隻貓」才有辦法真的走到 IMAGE 路線。

入口 B · /ask 指令

/ask 存在的唯一理由，是有三個地方永遠不會有 gateway 訊息事件：bot 沒被加進去的伺服器、群組私訊、兩個別人之間的私訊。在那些地方提及 bot、回覆 bot、貼連結全都沒有反應。

02

一次回覆的生命週期

關鍵設計：只有一支呼叫在關鍵路徑上（分類），其他全部提前開跑，跑錯了就丟掉。

  1. 上 🔀 流程圖表情，同時開三條線 三條線幾乎是同一瞬間啟動的。第一次讀歷史也在這裡，整輪只讀這一次。

同時開跑，互不等待

線 A · 直連供應商 附件上傳（Files API） 依當輪答案模型把當前訊息與被回覆訊息的附件推上對應的 Files API（Gemini 輪詢到 ACTIVE，Claude 上傳支援的圖片與 PDF 並設 48 小時 TTL、UTF-8 文字則內嵌；無金鑰或關掉開關時一律內嵌）。只有最後的答案會等它——分類讀的是純文字版本，所以路由從不卡在上傳上。
線 B · Proxy · 一支呼叫 路由分類 ＋ 思考強度 ＋ 第三人記憶 一支 triage 模型的 Responses 結構化輸出，也是唯一擋住分派的呼叫。強度只有 QA 會用。公開頻道的暱稱表裡有沒說話的成員時，同一支呼叫多帶伺服器記憶與候選清單，順便回答要讀誰的記憶；它不帶頻道歷史，所以從不等歷史讀完。
線 C · 本地為主 推測性上下文 頻道歷史（連同歷史裡的附件上傳）與語氣偏好，全部只讀不寫，所以走錯路線可以安全丟棄。伺服器記憶與程式端確定的參與者記憶在三條線開跑前就讀好了，因為分類那支呼叫要帶著它們。分類挑中的第三人，會在歷史與上傳都好了之後併進記憶區塊。

會合點：分類一回來，它挑中的第三人就交給線 C。強度和挑人都是分類本身的欄位，所以沒有另外的寬限期要等；分類解析失敗或撞上暫時性錯誤時一起退回保守值：走 QA、強度退回該輪抽中候選模型在 [global.models.slow].candidates 裡各自的預設 effort、只保留程式端確定的那幾個人。

  1. 分類回來，決定這輪的形狀 分類同時吐出這一輪的形狀：走哪條路、思考強度、要不要看 YouTube、要不要讀哪些連結貼文，有候選人時再加上要讀誰的記憶。解析失敗或暫時性錯誤就退回 QA。若有選中的連結來源，此刻固定一個共用的 180 秒截止時間。
  2. 換表情，分派 QA 上 💬 訊息表情，IMAGE 上 🖼️，VIDEO 上 🎬。IMAGE / VIDEO 永遠不會啟動連結貼文的抓取。
  3. 路線各自完成，最後上 ✅ 失敗則上 ❌ 並貼出錯誤 embed。如果答案已經開始串流了，錯誤會蓋在那則半成品回覆上，而不是另開一則——半成品沒有用量頁尾，單獨看會被誤讀成「答案答完了只是被砍掉」。
  4. 寫一筆使用紀錄 每則觸發訊息一筆，不是每個產出一筆。失敗也記，記在它當時走到的路線底下。
03

Router 到底決定了什麼

一支 proxy 呼叫，triage 模型 gemini-3.5-flash-lite，思考強度 minimal，讀的是純文字（附件只呈現成 [attachment: image] 這種標記）。

欄位可能值判斷準則何時生效
路線 QA / IMAGE / VIDEO IMAGE 只在「圖本身就是交付物」時才選：明確要求生成一張新圖，或明確要求修改既有的圖。VIDEO 是明確要求做影片或動畫，或附上影片檔（或回覆一則附有影片檔的訊息）並明確要求修改那段片、要拿回改好的片。路由只看得到 [attachment: file]，所以這一條要靠使用者自己講出「影片」。其餘全部 QA，含分析圖片、看網頁、做懶人包、總結頻道對話。曖昧一律偏向 QA 永遠；沒有 GEMINI_API_KEY 時 VIDEO 改走 QA
看影片 true / false 有 YouTube 連結而且使用者想知道影片內容。只是順手分享、問的是別的事，就是 false 只有 QA
連結來源 threads / facebook / instagram
/ twitter / douyin / bilibili		 有對應連結而且使用者想讓 bot 讀那則貼文的實際內容。每個來源獨立判斷，可以同時選多個 只有 QA
思考強度 low / medium / high medium 是常態，拿不準也給它。low 要爭取：什麼都不用查、不用算，看到的東西就能一行回完的閒聊。high 也要爭取：寫或除錯程式、數學與多步計算、多步分析或規劃，以及要求修改或延伸被回覆訊息裡的程式碼或計算。指著分類看不到的東西的短問句（「真的嗎」「這是什麼」）一律 medium 只有 QA
第三人記憶 候選成員的 id 最新這則用暱稱、合理的錯字或不會搞錯的間接說法指到某個候選人，而且他的記憶對回答有幫助。只在舊歷史、附件或連結裡出現過不算，曖昧就空著 公開頻道 ＋ 有候選人時才問

思考強度是同一支呼叫的一個欄位

輸出是 low / medium / high 三選一。medium 是常態，low 和 high 都要爭取來的：只有完全不需要查、不需要算、光靠看到的東西就能一行回完的訊息（打招呼、道謝、貼圖、純鬥嘴）才給 low；只有真的要推理才寫得對的工作（程式、數學、多步分析或規劃）才給 high。拿不準時給 medium；若分類呼叫本身失敗，則退回該輪抽中候選模型各自的 fallback effort。

分類讀的是純文字，看不到附件內容、連結背後的東西和短訊息背後的歷史，而且刻意不給它頻道歷史（給了它會從舊訊息裡挑連結來源）。這個盲點用規則補：指著它看不到的東西的短問句一律 medium，不會是 low。另外把貼圖標成「sticker」而不是「image」，因為純貼圖反應被當成截圖會被誤判成要回答的問題。

QA 拿到這個等級後，會用它覆蓋答案模型的預設強度，並顯示在回覆頁尾的 模型 (強度) 上。

為什麼是一支，不是三支

路由、強度、第三人記憶以前是三支呼叫。拿 239 則真實回覆重播實測：合併後延遲不變（p50 0.85 秒對 0.83 秒），路由與強度跟分開時的一致程度，等於分開的呼叫自己重跑一次的一致程度。第三人記憶反而變準：分開那支是帶 function tool 的呼叫，在沒人被點名的回合裡有 64% 會挑人；改成合併呼叫的一個欄位後是 0%。

代價是解析失敗或呼叫暫時失敗時所有欄位一起退回保守值。有候選人的那種形狀多帶了伺服器記憶，實測約 470 次沒有一次失敗。

04

QA 路線：預設，也是最複雜的一條

送進答案模型的東西，順序是固定的

  1. 能力說明文件放最前面。同一個部署的每則回覆它都完全一樣，擺前面對前綴快取最划算。它照部署的開關與金鑰改寫：沒有直連金鑰時省略音樂、影片、YouTube、深度研究，關閉 global.reply.file_api_enabled 或缺金鑰時改寫抖音與 Bilibili 為純文字，關閉 global.reply.feedback_enabled 時拿掉回饋按鈕說明；全部就緒時就是原文。這份英文文件是唯一描述「這隻 bot 會什麼」的地方，取代了被刪掉的 /help。只有 QA 帶它——交付一張生成圖時不是在回答「你會什麼」。
  2. 頻道歷史三個軸同時限制，誰先撞到算誰：最多 50 則、4000 字、每則額外算 40 字的開銷。從最新往回留，切在訊息邊界上。附件另有第三軸，最多 5 個真實檔案，超出的訊息退回純標記——一旦有一則被拒，比它更舊的全部一起拒，模型看到的檔案永遠是一段連到現在為止不中斷的區間。附件以內嵌送出時再多一道位元組預算（約 24 MB），超過的較舊訊息同樣退回標記；單一附件超過 20 MiB 則在模態閘就不內嵌。
  3. 伺服器記憶每個公會一份，直接讀檔沒有選取階段。私訊和 /ask 沒有。
  4. 使用者記憶程式端固定解析：發話者、被回覆訊息的作者、當前訊息裡明確提及的人，再加上公開頻道裡分類挑中的第三人。目標 8 人：程式端確定的人不受限，挑中的人只補剩下的名額。
  5. 語氣偏好只讀發話者一個人的，每一則回覆都無條件帶上，不做選取。它會覆蓋預設的嘴賤人格——但只管「怎麼講」，不管「講什麼」。
  6. 被回覆的訊息緊貼在當前訊息上方，附一段分隔說明：當前訊息指涉不明的東西就在這裡，包含它的附件。只會有一則，Discord 不會巢狀傳遞更上層的父訊息。
  7. 連結貼文區塊被路由選中的來源才有，按註冊順序排。
  8. 當前訊息永遠放最後，模型答的就是它。

另外，時間與地點（公會 id 或「私訊」）以 developer 權限放在頂層指令裡。地點只放 id 不放公會名稱——公會名是擁有者可控的文字，放進 developer 權限的區塊等於送人一個注入面。

答案的兩個後端

預設後端Proxy

由 [global.models.slow].candidates 定義候選池（預設為 gemini-4-neon，部署時可放多個模型並以 weight 加權抽樣，預設 1、0 可暫停該候選），每輪開頭抽好候選模型後，用路由給的強度（僅在路由失敗時退回該候選各自的預設 effort），開著 googleSearch 與 urlContext 兩個內建工具，串流。

這一輪不掛任何自訂 function tool，這是刻意的：一旦掛上，Gemini 那一輪會變成「呼叫工具就結束、正文空白」，接地引用歸零。

YouTube 後端直連

同一個模型、同一套系統指令、同樣的內建工具，只是改用 Interactions API 送出，讓 Gemini 自己去抓影片。

事件流會被翻譯回 Responses 的形狀，所以預覽、頁尾、標記處理、記憶排程整套完全共用。詳見 08。

串流的畫面行為

  • 思考預覽：第一個推理摘要 delta 到達時才建立回覆訊息，以 -# 小字顯示思路的最新幾行（最多 4 行 / 320 字）。第一個正文 delta 一到就整段換掉。
  • 編輯節奏：另一條任務以 1 秒為週期把快照寫回 Discord，主迴圈從不等 Discord。
  • 收尾：抽出所有內嵌標記 → 寫最終文字與用量頁尾 → 超過 2000 字就切成 follow-up → 然後才去生成附件媒體。切點依序找空行、換行、空格；都找不到才硬切，硬切也不會切斷提及或 emoji。放不下的程式碼區塊會在切點收起，下一則用同一個語言標籤重開。
  • 來源被刪：回覆改成不帶父訊息直接送進頻道，IMAGE / VIDEO 生成好的圖或片也一樣；回覆自己被刪則安靜結束，不會重發。

候選池抽樣與 🔄 重新生成

候選池與顯示名稱
[global.models.slow].candidates 定義每一輪 QA 按 weight 加權抽樣的候選清單（weight 預設 1，0 可暫停候選而不必刪除；每個模型各自帶一顆僅在路由失敗時生效的 fallback effort）。若設定非空的 [global.models.slow].display_name（例如 Gemini Next），系統提示詞與頁尾可見的模型名稱會改顯示該名稱並隱藏思考強度；計費、日誌與 reply.db 快照仍記錄真實回答模型與強度。
🔄 按鈕範圍
僅在開啟 global.reply.feedback_enabled 的伺服器與私訊 QA 回覆上出現（/ask、IMAGE、VIDEO 一律不提供），且只顯示到達到重抽上限為止：單一啟用候選（weight > 0）最多重抽 1 次；多個啟用候選最多重抽 啟用候選數 - 1 次，每一輪會排除同條重抽鏈上已抽過的模型。
重抽與刪舊順序
僅限原發問者（或 bot 擁有者）點擊，同一則回覆以鎖序列化防連點。重抽時會重取原始發問訊息、保留原思考強度並強制走 QA 路線（仍執行分類以保留 YouTube、連結貼文與第三人記憶判定）。只有在新回覆順利落地並寫入 reply.db 後，才會對舊回合補記一筆 regen 隱含倒讚（若使用者原本已點過明確 👎 則保留原原因不覆寫）並由後往前刪除舊分段訊息；任何失敗都會保留舊回覆與評分原狀。

重試與錯誤承接

哪些路徑會由 bot 端重試

LiteLLM 的 router 負責非串流與串流路徑的 fallback（num_retries: 0），SDK 端維持各自預設重試（OpenAI 與 google-genai）；bot 端不再為答案串流加外層重試迴圈。唯一保留 bot 端重試的是圖像生成（ImageGenerator），回傳空結果時會自動重試一次才報錯。

QA 答案與 IMAGE / VIDEO 交付後的人格化回話預設透過單次的 stream_answer 串流（global.reply.streaming_enabled = false 時改走 non_streaming.py 一次取回完整結果、不做即時預覽編輯）：在 /ask 上，QA 答案呼叫綁在 token 剩餘時間扣掉 60 秒的交付視窗內，逾時直接回報 Discord 視窗關閉；若串流中途失敗或未收到完成事件（如內容過濾、輸出預算用盡），回覆會保留已寫出的文字並在底下附上錯誤 embed。

答案模型自己在回覆裡下的標記

生不生圖、講不講話、記不記這件事，全部由答案模型在它自己的輸出裡決定。這樣文字、語音和媒體才會一致——事後再用一個分類器去猜是做不到的。

標記做什麼內容留在畫面上？走哪裡限制
generate-voice把包住的段落唸成語音會留Proxy TTS多段會串成同一個音檔，所以模型只挑值得聽的句子標
generate-image生成圖片並附上整段刪掉Proxy 圖像模型每則最多 9 張；使用者有傳圖時會變成編輯那些圖
generate-music生成一段音樂整段刪掉直連 Lyria每則 1 首，取第一個非空的

deep-research開一條研究討論串整段刪掉直連 agent只在公會的一般文字頻道、而且 bot 在那裡開得了討論串並寫得進去時，才提供這個標記

時機
全部在文字上畫面之後才跑，所以對文字的延遲是零。所有附件用一次編輯掛上去（Discord 的編輯會整組取代附件清單）。
不可用的直連功能
未設定 GEMINI_API_KEY 時（或研究頻道不支援時），提示詞裡不會提到對應標記（音樂、影片、深度研究），能力文件也不會寫成做得到。否則模型會照寫，然後標記被剝掉、什麼也沒產出，需求就這樣默默消失。
失敗
語音、圖、音樂、影片任一失敗，主要交付物照留，只在來源訊息加一個 ⏱️（語音逾時）或 ⚠️（其他，含圖、音樂、影片逾時）。/ask 上四種共用 token 剩下的時間：到點前做好的照樣掛上，還在算的放掉並留 ⏱️。
太大
先試著上傳到外部靜態站變成連結貼出來；連這個都做不到才丟棄加 ⚠️。
記憶標記的歸屬
由訊息的作者與公會決定，標記內容永遠沒有發言權。這是隔間邊界能維持結構性的關鍵。
06

IMAGE 路線

圖先送出去，再用同一則訊息串流一段人格化的回話。所以是「做圖的人把圖遞給你順便講兩句」，不是「冷冰冰地描述一張圖」。

  1. 載入來源像素當前訊息 ＋ 被回覆訊息的圖片，直接下載原始 bytes（不是 Files API handle，因為編輯要真的餵像素進去），先縮到長邊 3072。
  2. 提示詞導演gemini-4-hydrogen 開著搜尋工具，把一句話的請求擴寫成一段完整、能獨立成立的生成提示。它是忠實翻譯不是美術指導：只釐清「畫什麼」，不發明沒被要求的場景、風格、光線。命名的角色或作品會實際去搜尋確認外觀。來源圖也會一起送進去當接地依據。
    失敗或逾時就直接用原始請求，不會中斷。上限 120 秒。
  3. 圖像模型渲染gemini-nano-banana-2.1。有來源像素就走編輯端點，沒有就走生成端點。回傳空結果會自動重試一次才報錯。
  4. 送出太大就改成託管連結另發一則，人格回話也另開一則，不會蓋掉那個連結。生成到這裡為止都在硬失敗路徑上——圖是交付物，失敗要讓使用者知道。
  5. 人格化回話（盡力而為）gemini-4-hydrogen，不帶任何工具，把剛做好的圖以 base64 內嵌當焦點，串流到同一則訊息上。帶歷史與使用者記憶，不帶伺服器記憶，也不帶能力說明。這一步失敗完全靜音，圖留著。

推測性上下文是在圖已經上畫面之後才被取用的，所以那份 context 的建構完全和生成重疊，不佔時間。

07

VIDEO 路線

和 IMAGE 同形狀，但生成端整段是直連 Google，而且它有兩種互斥的模式。沒有 GEMINI_API_KEY 的部署走不了這條：分類判成 VIDEO 時，分派前就改走 QA 用文字回答，導演也不會先被呼叫。

  1. 先找來源影片依序看當前訊息、被回覆訊息，每則最多讀第一支影片。找到就進編輯模式。只有在找不到的情況下才去下載參考圖片——編輯絕不該被它會丟掉的素材拖慢。
  2. 模式 A · 有來源影片 → 就地編輯把整支片上傳 Files API 拿到 uri，然後以 task=edit 送出，提示詞就是使用者原話。導演在這裡被跳過：它只能靠圖片接地，對純影片編輯等於瞎猜，而且它是串在時間線上的。編輯模式下附帶的參考圖會被丟棄。
  3. 模式 B · 沒有來源影片當前 ＋ 被回覆訊息的圖片當主體參考（最多 3 張，每張都必須帶真實 MIME，空 MIME 會直接 400）。先跑一次導演擴寫，然後省略 task 欄位讓 omni 自己判斷是 image-to-video、reference-to-video 還是 text-to-video。純文字生成才會送 16:9。
  4. 取回影片用 delivery=uri，所以回來的是 Files 上的參照而不是 base64。互動回報 completed 時檔案可能還在收尾，所以下載本身帶有界重試。渲染本體上限 600 秒，兩端各再加 180 秒。
  5. 送出同 IMAGE。軟性拒絕會表現成「狀態不是 completed 且沒有影片輸出」，會被折進錯誤訊息。
  6. 看片，然後回話影片沒辦法內嵌，所以要再上傳一次 Files API（啟用上限 60 秒），bot 用這個 handle 真的把自己做的片看過一遍再回話。上傳失敗就沒有回話，也不會留下空訊息。
08

YouTube：觸發時機與整條路徑

這是整個流水線裡唯一的後端切換。不是第二輪、不是額外一趟，就是同一輪答案改用另一個 API 送出去。

四道閘門，全過才切換

  • 路由把 watch_video 判成 true 了嗎？
    • 否 → 走一般 Responses，連結只是連結
  • 在允許的範圍內掃得到 YouTube 網址嗎？
    • 先看當前訊息 → 內文、embed 卡片、轉發快照都算（YouTube 的連結卡就是那個連結本身）
    • 再看被回覆的那一則 → 一跳為止，而且會先剝掉 bot 自己的用量頁尾，免得頁尾裡的記憶標籤（那是使用者可控的顯示名稱）去挑到另一支影片
    • 都找不到 → 照常回答，只留一行日誌
  • 答案模型是 Gemini 嗎？有直連金鑰嗎？
    • 任一為否 → 退回 Responses，對使用者完全無感，只在日誌記下是哪一道閘擋的

切換以後發生什麼

請求端 已組好的輸入被翻譯成 Interactions 步驟 system / developer 區塊併進使用者步驟（Interactions 沒有 system 步驟，那些指令改走獨立的 system_instruction 欄位），連續同角色會合併。影片被附加在最後一個使用者步驟，也就是當前訊息，所以影片跟它要回答的問題貼在一起。影片部件帶 processing: agentic，模型只載入問題需要的片段或逐字稿，而不是每秒抽一格全部塞進來。已經上傳過的附件用既有 uri 引用，不會重傳。
回應端 事件流被翻譯回 Responses 的形狀 思路摘要、正文 delta、用量、完成事件全部改名成 Responses 的欄位，所以預覽、頁尾、標記抽取、記憶排程整套一行都不用改。用量只在完成時發一次（否則會重複累加）。接地引用回報成 「未回報」而不是 0——這個後端根本不用那個形狀報接地，寫 0 會被誤讀成沒接地。

來源訊息上會多一個常駐的 ▶️ YouTube 表情（在最後那個 ✅ 之後仍然留著），表示這則回覆是真的看過影片才寫的。這個表情刻意在建立串流器之前加上，否則這一趟 REST 往返會被算進「答案延遲」，讓唯一付這個成本的後端數字難看。

09

深度研究：觸發時機與生命週期

整段直連 Google，跑的是一個 managed agent，時間以分鐘計。就一份報告，沒有升級檔次、報告底下也沒有任何按鈕。

兩個入口

答案模型自己發動QA 標記

QA 回覆裡出現 deep-research 標記時。這個標記只在公會的一般文字頻道才會出現在提示詞裡——私訊或已經在討論串裡開不了新的 thread，不能讓模型承諾一件做不到的事。同樣的理由，bot 在這個頻道缺發言、附檔、開討論串或在討論串裡發言任一項權限時，標記也不提供（讀的是 bot 自己成員身分的頻道權限快取）。

提示詞要求它極度節制：一般問題就直接回答，不要開研究串。發動時要在可見回覆裡用人格語氣說一聲「要花幾分鐘」，不能承諾即時。

使用者直接下指令斜線指令

/deep_research，帶一個主題參數。頻道不對就直接擋掉，並說明只能在伺服器的一般文字頻道用。bot 在這裡缺上面那四項權限時，也在發任何東西之前就擋掉，回一句權限不夠；權限若在檢查之後才被收回，發錨點或開討論串被拒時一樣這樣說明。

會先發一則錨點訊息，討論串掛在它下面；主題是使用者輸入的，所以提及被限制到只能 ping 發起人。

  1. 搶佔名額一個人同時只能有一份研究在跑。已經有了就回覆現有討論串的連結。
  2. 生一個討論串標題triage 模型，走 proxy，15 秒上限。失敗就退回用 brief 的第一行。
  3. 開討論串、寫進資料庫、討論串掛的那則訊息上 🔬預設為 🔬（可在 config.toml 的 [global.emojis].research 覆寫為自訂表情），刻意跟一般 QA 的表情不同，一眼就看得出這是研究而不是回覆。
  4. 跑 agentantigravity-preview-09-2026，推理模型指定為 gemini-4-hydrogen，開著網頁搜尋與 URL 讀取（刻意不開程式執行：agent 的 bash/python 呼叫會以原始文字漏進報告裡）。用 background=true + store=true + stream=true，所以它的思路會即時畫在討論串開頭那則狀態訊息上。
  5. 串流斷了就重新接上SDK 會在 agent 還在工作時把長連線關掉，所以會帶著續傳 token 重新掛回去。
  6. 最終結果一律另外取一次完成事件刻意不帶報告本體，串流出來的只是即時視圖。所以永遠用一次終態查詢把報告拿回來，順便把「串流死了但 agent 沒死」的情況也一起收尾。
  7. 交付報告分段貼進討論串，第一段編輯進開場的狀態訊息，附上用量頁尾並 ping 發起人。agent 產的圖表也一起送。報告文字裡的任何提及都不會真的 ping 到人。
重啟之後

互動是掛在 Google 那邊跑的，所以重啟後會照著資料庫重新接上串流。但如果未設定 GEMINI_API_KEY，這個掃描會直接跳過而不是標記失敗——那一輪不管怎樣都已經在對面計費了，標成失敗只是把一份已經做完的報告丟掉。

另外，只要這個 cog 還在寫這條討論串，QA 就不會在裡面回話，免得蓋掉即時狀態；報告一落地就解除。

10

連結貼文：Threads / Facebook / Instagram / Twitter / 抖音 / Bilibili

六個來源同一個形狀。核心規則：路由沒有選中的來源，一個位元組都不會抓。順手貼的連結不花任何錢。

  1. 本地掃到連結只掃「模型實際看得到的文字」，所以掃描器不可能對一個模型從沒被展示過的連結開火。
  2. 路由決定要不要讀要「總結、解釋、分析、反應、問內容」才算要讀。只是分享、只是引用當背景，就不選。
  3. 選中的才開始抓，並固定一個共用截止時間180 秒，所有被選中的來源共用同一個截止點，跟後續的回覆準備工作重疊進行。
  4. 先拿到文字，再拿媒體先解析中繼資料（快，文字先落地），再抓媒體：圖片走該輪答案模型的附件渲染器（Gemini 或 Claude 啟用 Files API 且有對應金鑰時走 Files API，其餘模型、無金鑰或關閉 file_api_enabled 時以 base64 內嵌），影片則只限 Gemini 且啟用 Files API 時走 Files API。媒體那一步要在共用截止前留一段餘裕就結束，讀文字花掉的時間會從媒體那邊扣，慢了就降級成純文字，而不是整個被取消掉什麼都不剩。
  5. 失敗與逾時都有明確說法會注入一段說明，而不是什麼都不給：平台說貼文不在、這次讀不到（限流、5xx、斷線）、來不及讀，各是不同的說法，讀不到絕不會被說成貼文已刪除。所以模型絕對不會編一段內容出來，也不會宣稱它看過其實沒拿到的影片。
來源連結可以在哪裡抓什麼媒體門檻
Threads 當前訊息，或它回覆的那一則 整串對話（祖先鏈、目標貼文、它引用的貼文、底下的留言），但只吃目標貼文和被引用貼文的媒體。鏈與留言各有獨立上限，互不排擠 圖片走當輪附件渲染器（Gemini / Claude + Files API 上傳，其餘內嵌）；影片限 Gemini ＋ file_api_enabled ＋ 直連金鑰
Facebook 當前訊息，或它回覆的那一則 公開貼文的全文、圖片、互動數字，加上頁面預先載入的那幾則留言（不是整個留言區）。網址帶 comment_id 時會標出被指名的那一則。影片拿不到檔案，只帶連結 圖片走當輪附件渲染器（不吃影片）
Instagram 當前訊息，或它回覆的那一則 公開貼文的內文、輪播原圖、互動數字，加上頁面給的留言——登出狀態下一般貼文就是全部（實測 11 則報 11 則），這是它比 Facebook 多的地方；熱門貼文只有第一頁，最多帶 20 則。網址帶 /c/<id>/ 時會標出被指名的那一則。Reel 只帶連結，不上傳影片 圖片走當輪附件渲染器（不吃影片）
Twitter 當前訊息，或它回覆的那一則 貼文本身與它引用的那一則走官方嵌入端點；它上面的整串（最多 6 篇）和底下最熱門的回覆（第一頁，最多 30 則，回覆的回覆接在它回的那則後面）另外向第三方的 FxTwitter 要；長文與它引用的那一則的全文也向它要，因為官方端點在約 275 字處截斷，而且引用的那一則截了也不標記。FxTwitter 讀不到時退回官方端點附的上一層與截斷的文字，並明說留言這次讀不到。只吃目標貼文的圖，影片只帶連結，不下載 圖片走當輪附件渲染器（不吃影片）
抖音 只在當前訊息 影片或圖集，以 low 畫質下載（刻意低於給人看的展開品質） 圖集走當輪附件渲染器；影片限 Gemini ＋ file_api_enabled ＋ 直連金鑰
Bilibili 只在當前訊息 標題、簡介與影片，同樣 low 畫質 限 Gemini ＋ file_api_enabled ＋ 直連金鑰

為什麼只有 Threads、Facebook、Instagram 和 Twitter 會往回看一跳：它們抓的都包含留言，而那正好是各自的展開 cog 刻意不顯示的東西，所以「@bot 這篇底下在吵什麼」回覆在別人的連結上時，沒有別的東西可以回答。抖音和 Bilibili 帶的是影片而不是討論，而且都對頻率限制敏感。

四個社群來源同一個形狀

Threads、Facebook、Instagram 與 Twitter 的解析層現在回傳同一種結構：一個 chain（最後一個元素就是連結指到的那則貼文）加上 reply_branches（每則頂層留言一條分支，回覆接在它後面），而且貼文和留言共用同一個元素型別。入口也統一叫 parse_metadata。Twitter 的 reply_branches 在 FxTwitter 讀不到時是空的，但欄位照樣在——形狀一致的意思就是每個欄位在每個來源都代表同一件事，而不是各家給什麼就長什麼。Facebook、Instagram 和 Twitter 都沒有 Threads 那個 parse，這是規則不是遺漏：parse 會把目標貼文的影片下載到呼叫端給的暫存資料夾，由呼叫端負責刪掉，而只有 Threads 讀貼文時真的把影片寫到磁碟。

回覆 bot 的展開不算觸發

往回掃父訊息時不看 embed 卡片，只看作者真的打出來的文字。bot 自己的 Threads 展開會列出整串每則貼文的永久連結、ROOT 在最前面，如果照掃就會去讀串頂的貼文而不是人類貼的那一則。人打的連結一定在內文裡，所以不會漏。

提及規則

一則對著 bot 講的訊息（私訊或明確提及）只會被回答，不會被自動展開。所以一則帶連結的訊息只會付一次媒體下載的代價。反過來說，這也代表 AI 讀一次、展開 cog 讀一次，是兩件事。

附件是怎麼進到模型裡的

一句話原則：媒體靠上傳進模型，永遠不靠網址。 給 proxy 一個帶 http 的 file_id，它會把整個檔案抓下來轉成 base64 塞進請求裡，抓失敗還是無聲的。

收集 → 過濾 → 渲染

  • 這則訊息上有哪些可渲染的來源？
    • 附件、貼圖、embed 的圖與縮圖，以及轉發快照裡的同樣三種
    • embed 優先用 Discord 的代理網址（像 Threads CDN 那種來源會過期、也會擋沒帶特定標頭的請求）
    • bot 自己的語音檔會被跳過（文字已經在逐字稿裡了，重傳只是延遲加自我輸入重複）；音樂檔不跳過，因為描述被剝掉了，那個檔案是那首歌唯一的痕跡
  • 答案模型吃得下、這次的渲染方式也帶得走這個模態嗎？
    • 吃不下 → 在任何 LLM 呼叫之前就丟掉。這道閘查的是當下那一支答案模型，所以答案模型一換它就跟著換；價格表沒寫模態的 Gemini 模型預設文字、圖片、音訊、影片都收，其他模型才退回「文字 ＋ 圖片」保底值，連兩種渲染都看不到音訊與影片附件
    • 帶不走 → 同樣在這裡丟掉。內嵌渲染帶不了影音，所以走內嵌時影音不會被標給路由、不佔歷史的附件額度，同一則訊息的其他附件也照常進快取
    • 壓縮檔、執行檔、Office 與 OpenDocument 檔 → 直接丟（Files API 存得下，但模型生成時會 400，而回答請求沒有單檔重試，一顆老鼠屎會壞掉整鍋）
    • 其他文件、程式碼、結構化文字 → 一律當作可以走檔案路徑
  • 要用哪種渲染方式？
    • Files API 總開關關著 → 一律內嵌
    • 答案模型是 Gemini 且有 GEMINI_API_KEY → 上傳 Gemini Files API，引用完整 uri
    • 答案模型是 Claude 且有 ANTHROPIC_API_KEY → 圖片（≤ 10 MB）與 PDF（≤ 32 MB）上傳 Anthropic Files API（48h TTL），以帶 format 的 input_file 引用；UTF-8 文字檔內嵌為 input_text，影音在模態閘擋下
    • 其餘模型或缺少對應直連金鑰 → 內嵌（不跨 provider 共用快取）。圖片轉 base64、PDF 轉 base64、UTF-8 文字直接當文字放進去、影音在模態閘就已擋下
圖片預處理
上傳或內嵌前先縮到長邊 3072。從連結讀進來的動圖只送第一格靜態圖，透明背景照樣保留。
快取
以「訊息 id ＋ 編輯時間 ＋ 這次實際渲染的來源清單」為鍵，存的是 Files uri 與它們真正的到期時間，並保留 2 小時安全邊際。所以留在歷史視窗裡的訊息只上傳一次，不是每則回覆重傳一次。任一部件失敗就整筆不快取，下次重試。
兩種渲染
純文字版把附件呈現成 [attachment: image] 這種標記，給路由用，完全不碰上傳。完整版才做上傳，只有答案會等它。兩版共用同一次來源收集，所以路由絕不會標一個答案其實拿不到的附件。
歷史裡的死連結
只有歷史渲染會接受「已知會失敗」的快取結果——過期的 CDN 附件每一輪都會重新失敗一次。當前與被回覆的訊息不吃這一套，剛貼的附件遇到暫時性失敗，下一則回覆會重試。
總開關的存在理由
它不擋任何功能，擋的是好幾個功能底下的機制。曾經發生過上傳成功、模型卻被拒絕讀那個檔案的 provider 事故——那會賠掉整則回覆，因為壞掉的部件就在答案請求裡。

圖片與影片的第二條路：原始像素

IMAGE 路線的編輯、內嵌 generate-image 的編輯、以及 VIDEO 的參考影格，走的都不是 Files handle 而是直接下載 bytes——編輯需要真的把像素餵進去。同一輪裡如果圖片和影片標記同時出現，這批來源只會載入一次共用。

記憶：讀的路徑與寫的路徑是分開的

讀：先確定的，再選填的

  1. 程式端固定解析（沒有模型參與）當前發話者 → 被回覆訊息的作者 → 當前訊息裡明確提及的人。這串會經過去重與清理，本身不設上限；8 人是目標，只限制選填的人。
  2. 隔間邊界是「路徑」不是「過濾器」記憶是一件事一個檔案，存在允許讀它的那個資料夾底下。在公會裡讀 = 開「跨伺服器」＋「這個公會」兩個資料夾；在私訊裡讀別人的、或在群組私訊裡讀任何人的 = 只開跨伺服器那個；只有本人在自己的一對一私訊裡才讀得到全部。讀不到的隔間是一個從沒被打開的資料夾，沒有東西可以出錯，也沒有「失敗時該怎麼保守處理」的問題。
  3. 選填的第三人（由分類順便回答）只有在公開頻道、伺服器記憶的暱稱表裡有「沒說話但可能被指涉」的成員、而且程式端確定的人還沒佔滿名額時，分類那支呼叫才會多帶暱稱表與候選清單，多回答一題「最新這則訊息有沒有拐彎指到某個人」。挑中的人只收候選清單裡的，也不會擠掉程式端確定的那幾個人；分類解析失敗或暫時失敗就一個都不挑。
  4. 語氣偏好走另一條它刻意放在隔間樹之外，因為它記的是「你希望我怎麼講話」，跨伺服器天生安全。每則回覆無條件帶上，包含 IMAGE / VIDEO 的人格回話。

寫：模型在回覆裡標，背景再審一次

  1. 回覆落地時先掛一行「正在整理記憶⋯」只有這一輪真的下了記憶標記才會出現，而且是拼進本來就要寫的那次編輯裡，不多花一次 Discord 編輯。
  2. 背景審查（不擋回覆，失敗完全靜音）gemini-4-neon，走 proxy。它拿標記去對照逐字稿，並補上結構化欄位（類別、耐久度、分享範圍、正規化鍵）。之後還有一整排程式端的閘門會擋掉隨口提到的、假設性的、bot 自己建議的、關於別人的、信心不足的；重複的照樣記下，讓舊事實不過期。審查失敗就保留原狀，下次重啟再試一次，再失敗就放棄。
  3. 把結果換回那一行「✏️ 記下了 ⋯」、「🩹 不再記得 ⋯」，或者「✏️ 這次沒有記下什麼」。一定會有一個答案，因為畫面上那句承諾必須被收回。私下範圍的觀察只報數量不報內容。
  4. 攢夠了才整併成事實檔整併是另一支呼叫，按隔間扇出，每一支只看得到路由到它那個隔間的證據。資訊只會從跨伺服器流向公會，不會反向。一個隔間的事實文字超過門檻時，遺忘處理完之後再用另一支只帶事實的呼叫把它壓縮。所有記憶呼叫都用 medium：在 high 時壓縮會把輸出額度全部花在推理上，low 壓出來的批次則多半被當時（事實數的一半）的淨刪除上限擋下。這個上限現在放寬到九成，只擋幾乎清空整個隔間的批次。
  5. 遺忘是證據，不是刪除forget-memory 寫的是一筆「遺忘請求」，整併時交給一支只准刪除的呼叫，只能刪、不能改寫。所以回覆路徑本身沒有長出任何刪除能力，事實 id 也從來不會出現在答案提示詞裡。
伺服器記憶的兩道閘

私訊沒有，非 @everyone 可見的頻道也沒有。這兩道閘對答案模型是不可見的——所以在私訊或私密頻道下的 write-server-memory 標記會被安靜丟掉。標記來的時候長得跟其他標記一模一樣，是頻道說了算，不是模型。

唯一不靠標記的寫入 · /memory server catchup

有人在公開頻道下 /memory server catchup 時，bot 讀這個頻道從上一則「跟上進度」結果訊息之後的對話（最多 50 則，略過 bot），由記憶模型自己提出關於社群的筆記，再交給同一個背景審查，通過的才寫進伺服器記憶。這裡沒有答案模型在場，所以它是「答案模型自己標」唯一的例外，而且只寫伺服器記憶，從不寫任何人的個人記憶。

它不走上面那條記憶排隊：那條隊伍會把同一伺服器的兩輪併成只剩較新的逐字稿，也會把審查失敗報成「沒記到」。這裡的結果訊息是下一次從哪裡開始讀的節點，失敗必須分得出來，所以失敗的那則不算節點，下次會重讀。同一個伺服器 10 分鐘冷卻，整段必須在互動 token 失效前回報，否則公開的開始訊息就收不回來。

模型 (強度) · ⬆ 輸入 ⬇ 輸出 · $成本，價格表查不到這個模型時不顯示成本；設定非空的 [global.models.slow].display_name（如 Gemini Next）時模型與強度會改顯示該名稱（token 數與成本照常顯示）。模型名是串流實際回報的那個，不是被派發的那個——proxy 的 fallback 只有在這裡看得出來。
回饋按鈕與評分小字
開啟 global.reply.feedback_enabled 時，最終回覆（或長回覆最後一段）底下會附帶 -# 評分將用於架構改進⋯ 小字與常駐按鈕：👍 / 👎 供任何人評分（再按取消、切換覆寫，👎 另提供僅本人可見的原因按鈕、自由填寫與「取消評分」）；伺服器與私訊的 QA 回覆在未達重抽上限前另附 🔄，供原發問者就地重新生成。
📖 讀了
這則回覆讀了誰的記憶。超過兩個人會收斂成「等 N 人」。
✏️ 記下了 / 🩹 不再記得
背景審查完才會出現，換掉那句「正在整理記憶⋯」。一則回覆只會有一條記憶結果，而且這行不會進入之後的對話歷史。
媒體過大，改用連結
附件超過該處的上傳上限，改成託管網址。放在用量頁尾之前，否則之後的歷史渲染會把頁尾當成回覆內容的一部分。
/ask 上沒有表情

合成訊息在 Discord 上不存在，所以整條狀態鏈與所有常駐標記全部無聲跳過。唯一不能就這樣丟掉的是失敗提示（⏱️ / ⚠️）——照慣例那是被放掉的媒體唯一的痕跡，所以它們會被收集起來，在媒體步驟結束時寫成回覆上的一行。視窗快到期時還在算的媒體會被提早放掉，留下的那段餘裕就是用來寫這一行的。
